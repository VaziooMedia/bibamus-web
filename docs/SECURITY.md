# SÉCURITÉ — Documentation as-built

> Documente l'état réel des correctifs de sécurité appliqués, pas un historique de conversation. À mettre à jour à chaque nouveau correctif.
> Dernière mise à jour : 2026-10-15 (colonnes réservées de la table des profils ; avant : lectures de Stories, lectures et écritures de BibaPulse). Chaque ligne indique son niveau de preuve : **vérifié** (lu dans le code de l'app ou dans un script SQL / une fonction Edge livré) ou **déclaré** (appliqué dans Supabase d'après l'ancienne version de ce document ; aucun script livré ne permet de le rejouer ni de le vérifier).

> **Règle de publication.** Le dépôt `bibamus-web` est **public**. Ce fichier décrit ce qui est corrigé et les décisions en attente, mais **jamais** de détail exploitable (ni clé, ni faille décrite pas à pas). Le détail des points à examiner est tenu dans une note privée, hors du dépôt.

---

## Contexte

Fin août / début septembre 2026, l'audit automatique de sécurité de Supabase (Security Advisors) a révélé plusieurs failles réelles, en plus de nombreux avertissements mineurs. Ce document trace ce qui a été corrigé, ce qui reste ouvert, et une leçon technique importante apprise en cours de route.

## Leçon technique — scripts SQL et transactions

Plusieurs correctifs ont échoué silencieusement parce qu'une instruction en fin de script référençait une table qui n'existait pas encore (ou plus) : l'échec de cette seule ligne a annulé **tout le script**. Ça explique pourquoi certaines fonctionnalités (`pulse_incoming`, `pulse_sante`) sont restées absentes malgré plusieurs tentatives de correction.

**Conséquence retenue** : toujours vérifier les colonnes et tables réellement existantes (`information_schema.columns`) avant d'écrire une fonction qui les référence, plutôt que de se fier à la mémoire de ce qui « devrait » exister. Les scripts récents suivent cette règle (par exemple `bibamus-sql-solo-jetons.sql` : « Un seul bloc : tout réussit ou rien ne change »).

## Correctifs appliqués

### Vérifiés dans les scripts livrés

- **Visibilité « relations »** (BibaPulse et Stories). Elle reposait sur une table `follows` (suivi à sens unique) jamais utilisée en pratique : deux comptes Bibax mutuels ne se voyaient jamais. Elle repose désormais sur le système Bibax mutuel confirmé (`bibax_relationships`, statut `accepted`, dans les deux sens). C'est le cas de toutes les fonctions de lecture Pulse et de tags livrées, et de la fonction Edge `create-pulse-event`. Aucune référence à la table `follows` dans les scripts ni dans l'app (le suivi de *lieux* par `venue_follows`, lui, est actif). *Pour les Stories*, les fonctions `get_pulse_stories` et `get_room_stories` ne sont pas livrées ; leur version actuelle est vérifiée dans la base (voir plus bas).
- **Fonctions `SECURITY DEFINER` avec `search_path` fixé.** Dans les scripts livrés, presque toutes les définitions posent `search_path`, soit `public`, soit `public, extensions` (nécessaire quand `unaccent()` vit dans le schéma `extensions` : recherche d'étiquette, recherche tolérante).
- **Lecture limitée au connecté** : le fil BibaPulse (`get_pulse_feed`), le fil d'une fiche (`get_entity_pulse`), les commentaires et la liste des réactions d'une carte (`get_pulse_comments`, `get_pulse_reactors`) et les fonctions de tags exigent un utilisateur connecté, excluent les utilisateurs bloqués (dans les deux sens) et les cartes masquées.
- **Modération BibaPulse** : le signalant est toujours le compte connecté ; masquage automatique à 3 signalants distincts ; masquer / rétablir réservés à `can_moderate()` ; rien n'est supprimé. Voir `BIBAPULSE.md`.
- **Tags** : réglages de confidentialité par surface (`allow_pulse_tags`, `allow_story_tags`, `allow_profile_via_pulse_tag`, `allow_profile_via_tag`), blocage pris en compte, exécution retirée à `public` / `anon` sur les fonctions de tags récentes.
- **Rôles** : les règles d'accès admettent `editor`, `super_editor`, `moderator`, `admin`, `super_admin` (propositions IA, styles personnalisés, suppression de brouillons) ; les Stories officielles sont réservées à `admin` et `super_admin`. Dans l'app, `isAdmin` = rôle `admin` ou `super_admin`. Les suggestions Bibax et la recherche par nom excluent les comptes qui ne sont pas `role = 'user'`.
- **Lecture de ses propres données seulement** : journal de lecture d'étiquettes (`label_scans`), propositions de l'IA (`ai_proposals`) avec des rôles précis.
- **Écriture ouverte aux comptes connectés, par décision** : `drink_barcodes` et `drink_vintages` (lecture publique, écriture pour tout compte connecté, script `bibamus-sql-drink-barcodes-ecriture.sql` du durcissement du 2026-09-02). La version précédente de ce document les disait en écriture réservée au serveur : c'est inexact.
- **Bucket `pulse-photos`** : public, 5 Mo, JPEG / PNG / WebP, aucune écriture directe (tout passe par la fonction Edge `upload-pulse-photo`, authentifiée, avec contrôle Google Cloud Vision).
- **Vue `consumption_events`** : recréée en conservant ses options de sécurité (`bibamus-sql-solo-jetons.sql`).

### Vérifiés dans la base (résultat de requête, scripts non livrés dans le dépôt)

- **Table `salons` fermée à ceux qui n'y participent pas** (vérifié le 2026-10-09 par la liste des règles d'accès de la table). Lecture directe : les participants du salon et les administrateurs ; écriture directe : les administrateurs seulement ; aucun droit pour les visiteurs non connectés. L'app n'accède plus jamais à la table elle-même : elle passe par des fonctions serveur (`get_salon`, `save_salon`, `decline_salon_invite`, `get_club_round_buyers`), qui contrôlent l'appelant. Les fonctions voisines qui touchent un salon (`get_my_active_salons`, `ensure_salon_conversation`, `claim_water_alert_round_reminder`, `send_salon_invite`) vérifient elles aussi qui les appelle, et ne sont plus exécutables par les visiteurs. Les mises à jour en direct continuent d'arriver aux participants. Les scripts qui ont appliqué ces changements ne sont **pas** dans le dépôt (public) : ils décrivent l'état d'avant. Voir `BIBAROOM.md`.
- **Table `predict_games` (BibaPlay) fermée à ceux qui n'y participent pas** (vérifié le 2026-10-12 par le contrôle final du script : protection par ligne activée, deux règles, aucun droit pour les visiteurs). Lecture directe : les joueurs de la partie, son hôte, les membres du salon auquel elle est liée, et les administrateurs ; écriture directe : les administrateurs seulement ; aucun droit pour les visiteurs non connectés. L'app n'accède plus à la table elle-même, sauf pour l'écoute en direct : elle passe par `get_predict_game` (lecture par code, pour rejoindre) et `save_predict_game` (création et mise à jour), qui contrôlent l'appelant. Même méthode que pour les salons ; les scripts ne sont **pas** dans le dépôt (public).
- **Chat interne de l'équipe** (`admin_chat_messages`, `admin_chat_reactions`) : lecture et écriture réservées aux rôles de l'équipe (vérifié le 2026-10-09). Il n'existe pas de règle de suppression : une suppression réelle n'est pas possible depuis l'app (décision à prendre).
- **Exécution des fonctions `SECURITY DEFINER`** : les droits des visiteurs non connectés ont été retirés (vérifié le 2026-10-09), sauf pour les annuaires publics voulus et un petit nombre de fonctions encore en revue. Les comptes connectés gardent l'accès.
- **`story_bix`** (« Bixé » sur une story) : la lecture directe de la table n'est plus publique ; chacun ne gère que ses propres lignes. Le compteur et l'état « j'ai Bixé » passent par les fonctions de lecture (vérifié le 2026-10-09). Voir `STORIES.md`.
- **Journal de débogage WaterAlert** (`water_alert_debug_log`) : fermé aux visiteurs et aux comptes connectés ordinaires (protection par ligne ; lecture réservée aux administrateurs ; seules des fonctions du serveur y écrivent). Vérifié le 2026-10-12 par la liste des tables sans protection d'accès.
- **Notifications push** (fonction Edge `send-push-notification`) : la fonction n'accepte plus qu'un appel avec une **session de connexion valide** ou avec un **secret partagé** détenu par le serveur (utilisé par les rappels WaterAlert envoyés depuis la base). La clé publique de l'app, seule, est refusée. Pour un appel d'utilisateur, le serveur ne notifie que les destinataires autorisés par `push_allowed_recipients` (une relation Bibax acceptée, une conversation ou un salon en commun ; jamais soi-même, jamais une personne bloquée dans un sens ou dans l'autre, jamais quelqu'un qui a coupé ses notifications) et borne le nombre de destinataires et la taille du message. Le journal de la fonction ne contient que des compteurs. Vérifié en production le 2026-10-13 : appel avec la clé publique seule refusé, rappel WaterAlert reçu, notifications de message et « bien arrivé » reçues sur un téléphone. Le secret est rangé dans le coffre de Supabase et dans les réglages de la fonction ; il n'est dans aucun fichier du dépôt. Les scripts et la source de la fonction ne sont **pas** dans le dépôt (public).
- **Notifications du fil (`notifications_feed`)** : la fonction serveur `send_notification`, qui permettait à tout compte connecté de déposer dans le fil de n'importe qui une notification de type et de texte libres, ne sert plus qu'à un cas, le seul que l'app utilise : prévenir un Bibax qu'il est tagué dans une Story (`story_tag`). Elle vérifie que la Story est celle de l'appelant et porte bien ce tag, que le destinataire est un Bibax confirmé, non bloqué dans un sens ni dans l'autre, qu'il n'a pas refusé les tags dans les Stories, et ne crée qu'une notification par Story et par destinataire ; tout autre type est refusé. Aucune autre fonction de la base ne l'appelle, et la table n'accepte aucune écriture directe des comptes connectés (lecture et mise à jour de leurs propres lignes seulement). Vérifié dans la base le 2026-10-13 (fonction remplacée, droits contrôlés) et dans l'app (tag d'un Bibax dans une Story : notification reçue). Les autres notifications (invitation à un salon, demande Bibax, BibaPulse) sont créées par des fonctions du serveur. Le script n'est **pas** dans le dépôt (public).
- **Suggestions de Bibax** (`get_bibax_suggestions`) : la fonction montrait à des inconnus des champs de profil sans tenir compte des réglages de partage de la personne suggérée, et proposait aussi des utilisateurs bloqués. Elle applique maintenant les mêmes règles que la recherche par nom : nom, surnom, ville, localité et pays ne sont renvoyés que s'ils sont partagés ; la proximité (distance et critère des 30 km) ne joue que pour ceux qui partagent leur ville ; les bloqués, dans un sens ou dans l'autre, sont exclus. Vérifié dans la base le 2026-10-13 (fonction remplacée, droits contrôlés) ; le comportement a été testé sur une copie locale. Le script n'est **pas** dans le dépôt (public). Voir `BIBAX.md`.
- **Lectures de Stories** (vérifié dans la base et dans l'app le 2026-10-14) : `get_story_by_id`, `get_story_tags`, `get_room_stories` et `get_pulse_stories` contrôlent maintenant ce que l'appelant a le droit de voir : ses propres Stories, celles où il est tagué, celles d'un salon dont il est participant, celles partagées dans BibaPulse selon leur visibilité ; les blocages sont respectés dans les deux sens. Les visiteurs non connectés n'ont plus le droit de les exécuter. Les Stories d'un salon ne sont lisibles que par ses participants. Le comportement a été testé sur une copie locale. Les scripts ne sont **pas** dans le dépôt (public). Voir `STORIES.md`.
- **Lectures de BibaPulse** (vérifié dans la base le 2026-10-14 par les contrôles des scripts, et dans l'app : fil, commentaires, Bix, « j'arrive », Cheers, liste des réactions, notifications) :
  - **Tables fermées en lecture directe** : `pulse_events`, `pulse_comments`, `pulse_bix`, `pulse_incoming` et `pulse_sante` n'ont plus aucune règle de lecture ouverte à tous, visiteurs compris. Chacun ne relit directement que ses propres lignes (activités non masquées, commentaires, réactions), plus les administrateurs pour les activités et les commentaires. L'app n'a pas besoin de plus : elle n'y fait que des écritures directes, et toutes ses lectures passent par des fonctions du serveur.
  - **Fonctions de lecture contrôlées** : `get_pulse_comments` et `get_pulse_reactors` ne renvoient rien quand l'appelant n'a pas le droit de voir la carte (même règle que le fil : carte non masquée, aucun blocage dans un sens ou dans l'autre avec son auteur, et c'est la sienne, ou elle est publique, ou son auteur est un Bibax confirmé) et n'affichent pas les personnes bloquées ; elles ne sont plus exécutables par les visiteurs. `get_pulse_event_preview` (aperçu d'un lieu pour les notifications) n'est plus appelable que par le serveur.
  - **Compteurs d'activité** : les fonctions qui tiennent à jour le nombre de Bix, de « j'arrive », de Cheers et de commentaires sous chaque carte (`sync_pulse_*_count`) s'exécutent avec les droits du serveur, comme leurs voisines `refresh_pulse_*_count`, pour compter juste quelle que soit la personne qui réagit. Le compteur de commentaires ne compte que les commentaires affichés (ni supprimés, ni retirés par la modération) ; « Bixé par » montre le dernier Bix encore présent. Les compteurs erronés de quatre anciennes activités (d'avant la mise en place de ces fonctions) ont été remis à leur vraie valeur ; aucune autre activité n'était fausse.
  - Testé sur une copie locale (comportement complet rejoué, compteurs comparés à un calcul indépendant, variantes volontairement cassées des scripts pour vérifier que les tests les détectent). Les scripts ne sont **pas** dans le dépôt (public). Voir `BIBAPULSE.md`.
- **Écritures de BibaPulse** (vérifié dans la base le 2026-10-14 par les contrôles du script, et dans l'app : commentaire, Bix, « j'arrive », Cheers, retraits, notification reçue) :
  - **Commentaires, Bix et « j'arrive »** : ils ne se déposent plus que sous une activité que la personne connectée a le droit de voir (même règle que le fil : carte non masquée, aucun blocage dans un sens ou dans l'autre avec son auteur, et c'est la sienne, ou elle est publique, ou son auteur est un Bibax confirmé), et toujours à son propre nom. Une écriture refusée ne crée ni ligne ni notification. Retirer son propre Bix ou son propre « j'arrive » reste toujours possible.
  - **Cheers** : la fonction `toggle_pulse_sante` refuse un appel sans compte connecté et vérifie la même règle avant d'ajouter un Cheers ; en retirer un reste possible. La table n'accepte plus d'écriture directe : l'ajout ne passe que par la fonction.
  - **Modification et suppression** : modifier un commentaire ou une activité par l'API est réservé aux administrateurs, et plus personne ne supprime un commentaire ou une activité par l'API. L'app n'utilise aucune de ces modifications ; la modération (masquer / rétablir) et le masquage automatique passent par des fonctions du serveur, qui ne sont pas concernées. Un auteur ne peut donc plus réécrire sa propre activité ni modifier ses commentaires directement.
  - La règle interne de visibilité est exécutable par les comptes connectés (elle ne répond que pour la personne connectée) ; les visiteurs n'y ont pas accès.
  - Testé sur une copie locale (écritures comparées à un calcul indépendant de la visibilité sur plusieurs comptes et activités, notifications et compteurs vérifiés, variantes volontairement cassées du script pour vérifier que les tests les détectent). Un retour arrière a été préparé et testé. Les scripts ne sont **pas** dans le dépôt (public). Voir `BIBAPULSE.md`.
- **Profil : colonnes réservées** (vérifié dans la base le 2026-10-15 par le contrôle du script ; relecture du code de l'app : aucun écran n'écrit ces colonnes) : la garde posée sur la table des profils (fonction `protect_role_field`, déclencheur avant modification) couvre désormais, en plus du rôle, du droit de modération et de l'état actif, les colonnes de blocage (motif et date), le code Bibax, la date d'inscription et l'état d'approbation Business. Chacune est réservée aux rôles habilités ; un compte ordinaire ne modifie que ses champs de profil libres. Les comparaisons de la garde sont sûres face à une valeur vide, et les écritures faites par le serveur lui-même ne sont pas concernées. Lecture de la table : chacun ne lit que sa propre ligne (les administrateurs lisent toutes les lignes).
- **Clubs : écritures sur les membres** (vérifié dans la base le 2026-10-15 par le contrôle du script) : l'entrée dans un club respecte son mode (ouvert ou sur invitation : membre actif ; sur demande : demande en attente) et se fait toujours à son propre nom ; seul le créateur d'un club encore vide en devient administrateur. Valider une demande, promouvoir ou rétrograder est réservé aux modérateurs et administrateurs du club, jamais sur soi-même ni sur un administrateur ; chacun peut quitter un club, sauf son dernier administrateur actif. Nommer un administrateur passe par la fonction `set_club_admin`, réservée aux administrateurs du club ; un club qui a des membres actifs garde toujours au moins un administrateur actif, ce que la base vérifie aussi elle-même à la fin de chaque opération. Un membre ne peut ni changer de club ni d'identité, ni redevenir « en attente ». La modification et la suppression directes d'un club par l'API ne sont plus possibles (l'app n'en fait aucune), et les visiteurs non connectés n'ont plus aucun droit sur les tables de clubs. Testé sur une copie locale (toutes les combinaisons d'acteurs, de clubs et d'opérations comparées à un calcul indépendant, parcours de l'app avant et après, variantes volontairement cassées du script pour vérifier que les tests les détectent). Un retour arrière a été préparé et testé. Les scripts ne sont **pas** dans le dépôt (public).

### Déclarés (appliqués dans Supabase, scripts non livrés)

- **RLS activée sur 8 tables publiques**, lecture publique conservée, écriture retirée du client. Tables citées par l'ancienne version : `taxonomy_terms`, `taxonomy_terms_translations`, `product_translations`, `brand_translations`, `producer_translations`, `establishment_translations`, `drink_barcodes` et `spatial_ref_sys`. Pour cette dernière (table système PostGIS), la RLS est impossible à activer : laissée telle quelle. **Attention** : les six premières tables n'apparaissent ni dans l'app ni dans les scripts livrés (voir `MULTILINGUAL.md`) ; et `drink_barcodes` a depuis une écriture ouverte aux connectés (voir plus haut).
- **17 fonctions sans `search_path` fixé** corrigées par `alter function ... set search_path = public`, appliquées par introspection (`pg_proc`) plutôt qu'en devinant chaque signature.
- **7 buckets publics** : règle de lecture autorisant le *listage* complet des fichiers retirée (inutile pour l'accès par URL directe). L'app ne liste jamais un bucket ; elle n'a qu'un appel direct de stockage (URL signée des pièces jointes de messagerie).
- **Fonctions internes** retirées de l'exécution publique : `anonymize_before_user_delete`, `audit_content_changes`, `audit_profile_changes`, `fill_submitted_by`, `sync_open_reports_count`, `handle_new_user`, `merge_entities`.

## Connu comme non résolu

- **Extensions dans le schéma `public`** (PostGIS ; `unaccent` et `pg_trgm` aussi) : signalé par l'auditeur, mais déplacement jugé trop risqué (toute la logique de proximité et de recherche en dépend) — laissé tel quel volontairement.
- **Protection contre les mots de passe compromis** désactivée dans les réglages Supabase Auth (Authentication → Password Security) — à activer manuellement, ce n'est pas du SQL.
- **Clé d'autocomplétion d'adresse** : la clé Geoapify est lue par le navigateur (variable d'environnement `VITE_`, donc visible dans l'app). Elle doit être restreinte par domaine chez le fournisseur ; cette restriction n'est pas vérifiable depuis le code.
- **Revue de sécurité du code en cours** : plusieurs points (règles d'accès trop larges sur certaines tables internes, résidus de code d'accès administrateur, contrôles complémentaires sur BibaPulse) ont été relevés lors de la vérification de la documentation du 2026-10-09. Les lectures de Stories, ainsi que les lectures et les écritures de BibaPulse, sont corrigées (voir plus haut) ; le détail des points restants est dans une note privée et sera traité avant d'être décrit ici.
- La majorité des avertissements restants de l'auditeur concernent des fonctions `SECURITY DEFINER` **volontairement publiques** : les RPC appelées par l'app. Pour les fonctions de données personnelles, une garde de connexion est bien présente (`auth.uid() is not null`) ; ce n'est pas le cas des lectures d'annuaire public, qui sont voulues ouvertes. Ce ne sont donc pas toutes de fausses alertes : chacune doit avoir sa justification.
