## Principe général

Plateforme orientée ordinateur, séparée de l'app principale, pour encoder et vérifier les fiches (établissements, produits, marques, producteurs, shops) plus vite que sur mobile, et pour piloter l'app (modération, drapeaux de fonctionnalités, discussion d'équipe). Dépôt GitHub distinct (`VaziooMedia/Bibamus-Management`), annoncée sur `admin.bibamus.app` **(dépôt admin)**.

Les indices d'un **même backend Supabase** que `bibamus-web` sont concordants — scripts « plateforme de gestion » placés dans les migrations communes (`ai-proposals-rls`, `styles-personnalises`, `schema-admin-chat*`), mêmes noms de fonctions dans la couche de données copiée — mais la preuve définitive (l'URL du projet) n'est pas lisible dans ce dépôt.

## Ce que `bibamus-web` contient de la plateforme (copies orphelines)

`bibamus-web` embarque des copies de composants d'administration **jamais importées depuis `App.jsx`** : `UserDetailPanel`, `DrinksScreen`, `DrinkDetailPanel`, `BreweryDetailPanel`, `BrandDetailPanel`, `SimpleEntityPanel`, `DataTable`, `ServerDataTable`, `DataBaseOverviewScreen`, `OpeningHoursEditor`, `GooglePlaceLinker` (`VenuesScreen` et `VenueDetailPanel`, du même type, ont été retirés le 2026-11-03). Elles importent des fonctions **absentes** de `sharedDirectories.js` (`createAppUser`, `updateAppUserProfile`, `deleteAppUser`, `mergeEntities`, `searchGooglePlaceMatches`, `linkGooglePlace`, `unlinkGooglePlace`, `setNoGooglePresence`). Conséquence : une preuve trouvée dans ces copies **ne prouve pas** l'état du dépôt de gestion, dont elles sont des versions plus anciennes ou partielles.

**Depuis le 2026-11-05, plus aucun outil d'administration n'est atteignable dans l'app, même pour un compte `admin` ou `super_admin`** : les écrans « Brasseries » et « Marques » (`BreweriesAdminScreen`, `BrandsAdminScreen`), l'import de données (`ImportDataScreen`, bouton des Réglages compris), l'édition d'un produit (`DrinkFormScreen`), l'écran « Accès administrateur » et les boutons Certifier / Décertifier / Supprimer du répertoire / Accepter / Refuser / Éditer des fiches Produit, Producteur et Marque ont été retirés (décision de Mehdi). Tout cela se fait depuis la plateforme de gestion ; la modification d'une fiche par son gérant passera par la future plateforme Business. Le bloc de lecture « Admin — Chiffre d'affaires » des fiches Produit et Lieu a lui aussi été retiré le 2026-11-05 : l'app n'a plus aucun écran réservé aux administrateurs.

## Gestion des utilisateurs

La gestion des utilisateurs **existe** (la version précédente de ce document, comme `DATABASE.md`, la disait pour l'un « construite », pour l'autre « non encore construite »). Ce que montre la copie de `UserDetailPanel` :

- Création et édition d'un compte : prénom, nom, surnom, date de naissance, pays, commune. **Nom d'utilisateur (@nom)** : voir le point suivant (la base refuse l'écriture directe de ce champ, y compris depuis cette plateforme : voir `DATABASE.md`). La commune est obligatoire (validation bloquante), comme pour l'enregistrement du profil dans l'app ; à l'inscription dans l'app, seul le pays est demandé.
- **Nom d'utilisateur (@nom) : comptes, lieux, marques et producteurs** (livré le 2026-10-24 ; lu dans le dépôt de gestion à la livraison, **(dépôt admin)** : non revérifié depuis) : une section repliable « Nom d'utilisateur » (repliée au départ, même en-tête que les autres sections de chaque fiche), visible seulement pour `admin` et `super_admin` (le rôle est transmis aux fiches par `MyRoleContext`) et seulement sur une fiche **déjà créée** ; dans la fiche d'un compte, avant « Informations » ; dans celles d'un lieu, d'une marque et d'un producteur, juste après « Dénomination » (composant `UsernameAdminField`). Elle relit le nom actuel dans la base à chaque ouverture, vérifie le nouveau nom pendant la frappe (`admin_check_username`, différée de 0,4 s), demande une confirmation (« Remplacer @ancien par @nouveau »), puis l'applique par `admin_set_username`. Sans limite de changements ; un nom réservé est permis, et changer seulement la casse aussi ; la forme, un nom déjà pris et le nom identique au nom actuel sont refusés, avec la phrase renvoyée par le serveur (la plateforme n'en invente aucune). Un changement marque le nom comme « changé » : un compte dont le nom a été changé par l'équipe ne peut plus le changer lui-même (la confirmation le dit pour un compte jamais changé). Les écritures habituelles de ces fiches (enregistrer, créer) n'envoient jamais `username`. Le changement par les gérants de fiches, depuis la plateforme Business, n'est pas construit. Voir `DATABASE.md`.
- `CityAutocomplete` pour la commune. La copie de `bibamus-web` lit `CITIES_BY_COUNTRY[country]` **sans conversion** ; la conversion code pays interne ↔ libellé que décrivait l'ancienne version n'existe que, si elle existe, dans la version du dépôt de gestion **(dépôt admin)**. Le panneau passe un code interne (`COUNTRIES` y est un tableau `{ code, fr }`, alors que dans `bibamus-web` c'est un tableau de chaînes) : les deux `constants.js` diffèrent.
- Attribution d'une `app_language` (`fr`, `nl`, `en`, `de`) — voir `MULTILINGUAL.md`.
- La création appelle `createAppUser(...)` ; la fonction Edge `admin-create-user` citée par l'ancienne version n'est **dans aucun fichier lu** **(dépôt admin)**.
- Statut administrateur dans l'app : automatique, déduit du rôle (voir `PROFILE.md`).

### Propositions de l'IA (`ai_proposals`)

- Table `ai_proposals` (scripts `ai-proposals`, `ai-proposals-rls`, `fix-entity-id-type` : `entity_id` en texte). **Rien n'est jamais écrit automatiquement dans une fiche** : l'IA propose, un administrateur valide.
- Fonction Edge `ai-complete-entity` : réservée aux cinq rôles du personnel (contrôle du jeton et du rôle), appelle OpenAI avec recherche web, n'accepte que `entityType = "drink"`. Champs complétables : styles, année de lancement, région d'origine, nom alternatif, IBU, couleur EBC.
- Le service OpenAI reçoit donc des noms de produits ; le service de lecture d'étiquettes (`read-label`, côté app) lui envoie en plus des photos d'étiquettes.

### Styles personnalisés

Table `custom_beer_cider_styles` : une ligne est soit un style **ajouté à la main** (code préfixé `perso_`), soit une **modification d'un style de la liste figée** du code (même code que lui : nouveau nom, nouveau groupe, ou masqué = supprimé, colonne `hidden`). Nom unique parmi les styles visibles **d'une même famille** (casse et espaces ignorés ; depuis le 2026-11-25 : « Lorsque je veux renommer un style d'un cidre, ça me met que ce style existe déjà côté bière. Il faudrait bien séparer »). Famille « cidre » = groupes « Cidre — … » ; famille « bière » = tous les autres (« Autres styles » compris). Le message « existe déjà, dans le groupe … » (renommer, déplacer ou ajouter un style) ne se déclenche donc plus pour un nom pris de l'autre côté ; la base applique la même règle (index `custom_beer_cider_styles_fr_unique`, voir `DATABASE.md`). Un style déplacé d'une famille à l'autre est contrôlé dans la famille de son groupe d'arrivée. Une seule colonne de libellé `fr`. Lecture publique, écriture réservée aux cinq rôles du personnel.

**Styles séparés par sous-catégorie (Mehdi, 2026-11-24 : « les styles alloués à la sous-catégorie Bières s'affichent lorsque Bière est choisi, et pareil pour les Cidres »)** : dans la fiche produit « Bières & Cidres », l'accordéon de styles (`BeerCiderStylePicker`) ne montre que les groupes de la sous-catégorie choisie — **« Bière » : les 12 groupes de bières (231 styles)** ; **« Cidre » et « Poiré » : les 6 groupes « Cidre — … » (Base produit, Douceur / sucrosité, Effervescence, Méthode & fermentation, Spécialités, Origines / traditions stylistiques ; 60 styles)**. Poiré n'a pas de liste à lui pour l'instant : il partage celle du Cidre (qui contient déjà « Poiré / Perry » et « Poiré de glace »). La famille d'un groupe se lit dans son titre (préfixe « Cidre — » = cidres, sinon bières ; le groupe « Autres styles » qui recueille les styles orphelins est montré dans les deux cas) ; la famille d'un style est celle du groupe où il se trouve aujourd'hui, modifications faites depuis la gestion comprises : un style **ajouté à la main** suit donc le groupe dans lequel il a été rangé (fonctions `styleGroupsForSubtype`, `styleFamilyOfCode`, `stylesForBeerCiderSubtype` dans `src/data/customStyles.js`). Les menus « Groupe… » de « + Ajouter un style » et « Groupe du style » de « Modifier la liste » ne proposent que les groupes de la sous-catégorie ouverte (les doublons de nom et les codes déjà pris restent vérifiés sur la liste entière). **Un style de l'autre famille resté coché** (ex. produit passé de Bière à Cidre) **n'est ni affiché, ni compté dans « (n sélectionnés) », et il est retiré à l'enregistrement** — même règle que pour les Softs & Eaux. Au 2026-11-24, avant la mise en ligne, 1 bière portait un style de cidre et 5 cidres un style de bière (sur 1 025 produits ; aucun poiré) : **corrigés par un bloc SQL le même jour** (lancé à la main, qui s'annule s'il ne touche pas exactement 5 cidres et 1 bière) — les 5 cidres sans alcool (Somersby Apple, Mandarin, Pear et Wildberries 0,0 %, Strongbow Red Berries 0.0 %) passent de `perso_alcohol_free` (style ajouté à la main, rangé dans un groupe de bières) à `cidre_sans_alcool` (« Cidre sans alcool », groupe « Cidre — Spécialités ») et gardent `perso_flavored_cider` ; la bière « Badjawe Éphémère N°2 - Bellini » passe de `brut` (style de cidre) à `champagne_beer_biere_brut` (« Champagne Beer / Bière Brut », au choix de Mehdi). Plus aucun produit ne mélange les deux familles ; un nouveau mélange (changement de sous-catégorie) se règle à l'enregistrement. Rien ne change dans la base ni dans l'app publique (les noms de styles s'y affichent comme avant). Testé en simulation : bière (12 groupes, 0 « Cidre — »), bascule Bière → Cidre (6 groupes, étiquettes de bière masquées), Poiré (6 groupes), menus de groupe limités, cidre portant « Brut » + « IPA » (enregistré avec « Brut » seul).

Dans la fiche produit bière / cidre (Niveau 1 → Style(s)), « Modifier la liste » permet de renommer, de changer de groupe ou de supprimer n'importe quel style, y compris ceux de la liste figée. La suppression annonce d'abord le nombre de produits concernés, puis retire le style de ces produits et de la liste en une seule opération (fonctions `count_drinks_with_beer_cider_style` et `delete_beer_cider_style`, réservées au personnel). Un style de la liste figée supprimé est **masqué**, pas effacé (il vit dans le code) ; un nom supprimé peut être ajouté de nouveau (nouveau code `perso_…`). Un style rangé dans un groupe qui n'existe plus apparaît dans « Autres styles ».

**Ordre des styles (Mehdi, 2026-11-25 : « Il faudrait aussi pouvoir modifier l'ordre des styles (la position). À faire partout sur tous les styles de toutes les sous-catégories »)** : dans le panneau d'un style (mode « Modifier la liste »), une ligne **« Place dans le groupe : N sur M »** (**« Place dans la liste »** pour une liste sans groupe, comme l'eau, le whisky ou le rhum) et quatre boutons : **« En premier »**, **« ◀ Avancer »** et **« Reculer ▶ »** (d'un rang), **« En dernier »**. Chaque clic **enregistre aussitôt** (comme les flèches ↑ ↓ des autres listes) : pas besoin de « Enregistrer » ; les boutons sont grisés aux extrémités et pendant l'enregistrement ; si la base refuse, le message d'erreur s'affiche dans le panneau et la place ne change pas. Un style ne bouge **qu'à l'intérieur de son groupe** (les groupes eux-mêmes gardent leur ordre) ; changé de groupe, il se place **en dernier** dans son nouveau groupe. **Partout** : les 35 listes de styles (clés se terminant par `_style` : Softs & Eaux, Boissons chaudes, Vins & Bulles, Cocktails / Mocktails / RTD, tous les Spiritueux — `isStyleList`, `orderable: true` dans `src/data/customLists.js`) **et** la liste des Bières & Cidres (clé `beer_cider_style`, constante `BEER_CIDER_STYLE_LIST_KEY` dans `src/data/customStyles.js`). Les autres listes (arômes, accords, dérivés…) gardent leurs flèches ↑ ↓ ou leur ordre de départ. **Où c'est enregistré** : table `custom_list_order` (voir `DATABASE.md`), aucun script SQL de plus. Pour une liste **à groupes**, chaque entrée de `codes` s'écrit **`<titre du groupe>::<code>`** (ex. `Cidre — Base produit::cidre_de_pomme`) : un code présent dans deux groupes (7 styles de bière, comme `cold_ipa`) a ainsi une place indépendante dans chacun, et les entrées des autres groupes sont conservées telles quelles à chaque déplacement ; pour une liste sans groupe, `codes` reste la suite des codes (`eau_sparkling`, `whisky_…`). Un style absent de l'ordre reste à la fin de son groupe, comme pour les autres listes (fonctions `orderGroups`, `moveWithinGroup`, `moveInOrder` — qui accepte -1, 1, « first », « last » — de `customLists.js` ; composant `PositionControls.jsx` ; panneaux `StyleManagePanel` pour les bières & cidres et `ListItemManagePanel` pour les autres listes de styles). L'ordre se voit dans la gestion : pastilles de l'accordéon de styles de la fiche produit (`GroupedListField`, `GroupedListPicker`, `BeerCiderStylePicker`) et copie détaillée `DrinkDetailPanel`. **L'app n'est pas touchée** : elle n'affiche les styles d'un produit que sous forme de pastilles, dans l'ordre propre au produit (celui dans lequel les styles ont été cochés), et lit les libellés par code ; la place d'un style dans la liste de la gestion n'y change rien. Scripts : `styles-personnalises` (la table), `styles-modifier-supprimer` (colonne `hidden` et deux fonctions), puis `styles-regle-des-codes` (retire la règle « code préfixé `perso_` », incompatible avec la modification d'un style de la liste figée). Quatre champs : **volume** par défaut (centilitres ; grammes pour un snack), **type de service** par défaut (« — », Bouteille, Canette, On Tap, Au verre, PET, Brique, Carton ; la même liste sert au type de service par défaut du shot d'un spiritueux ; codes `bouteille`, `canette`, `fut`, `verre`, `pet`, `brique`, `carton`, liste `DEFAULT_SERVING_MODES` dans `src/data/beerCiderStyles.js` de la plateforme), **Valeur € par défaut** (vide au départ) et **Valeur jeton par défaut** (affichée à 1 quand la fiche n'a pas de valeur : enregistrer la fiche écrit donc ce 1 en base). Texte d'aide de la section **supprimé le 2026-11-06** (« Cochez les dérivés que ce… »). Code : `customLists.js` (`SPIRIT_DERIVATIVE_LIST.volume`, `parseDerivativeVolume`, `derivativeVolumesToSave`, `derivativeVolumesToForm`), `FlatListEditor.jsx` / `FlatListField.jsx` (colonne `rowValues`), `DrinkDetailPanel.jsx`, `sharedDirectories.js`. Clé `beer_derivative` dans `custom_list_items` / `custom_list_order`, codes `perso_…`. Aucun dérivé n'est fourni d'office : la liste commence vide.

Un champ vide affiche « valeur du produit ». **Ordre PROPRE À CHAQUE PRODUIT (décidé et écrit le 2026-11-06 ; branche `claude/derives-tri-par-produit`)** : un rhum a le cola en premier, un gin le tonic. C'est l'ordre des codes cochés dans `drinks_directory.derivatives` (aucune colonne de plus, aucun SQL) : le tableau montre d'abord les dérivés **cochés, dans l'ordre du produit**, puis les non cochés (ordre commun de la liste) ; cocher un dérivé le met **à la fin des cochés**, le décocher le renvoie parmi les non cochés. Les flèches ↑ ↓ ne se trouvent **que sur les lignes cochées** (« Monter » grisé sur le premier coché, « Descendre » sur le dernier coché), elles changent l'ordre **de la fiche** et s'enregistrent **avec la fiche** (« ✓ Enregistrer »), plus tout de suite ; elles sont masquées pendant le mode modification. Elles n'écrivent plus `custom_list_order` : l'ordre commun de la liste ne sert plus que de départ (interrupteur ON : tous les dérivés cochés dans l'ordre commun, à ranger ensuite) et pour les lignes non cochées ; l'application suit l'ordre du produit pour ses pastilles (le premier de la fiche est le premier proposé). Valable pour les bières comme pour les spiritueux. Un code coché qui n'existe plus dans la liste reste dans la fiche, à la fin, sans s'afficher. Tri automatique par popularité : pas retenu pour l'instant, l'ordre se règle à la main.
- **Énergie du dérivé, PAR PRODUIT (décidé et écrit le 2026-11-08 ; dépôt de gestion, pull request #60, branche `claude/derives-kcal-produit`)** : dans « Dérivés du produit » (bières, spiritueux, thés et infusions), chaque dérivé **coché** a un champ **« Kcal/100ml. »** propre au produit, avant la colonne « Volume (cl.) » des spiritueux ; nombre de 0 à 900 (virgule acceptée), facultatif, contrôlé à l'enregistrement (message « Énergie d'un dérivé — {nom} : … »). Enregistré avec la fiche (« ✓ Enregistrer ») dans `drinks_directory.derivative_kcal` (`{code du dérivé: kcal}`, voir `DATABASE.md`), effacé si le dérivé est décoché ou supprimé, ou si l'interrupteur passe sur OFF ; enregistré aussi pour les thés et infusions. Règle : **la valeur saisie pour ce produit et ce dérivé remplace entièrement l'énergie du produit ; sans valeur, l'app garde l'énergie du produit — jamais une valeur par défaut propre au dérivé** (Jupiler + Mazout 52, Leffe + Mazout 60). Les listes communes de dérivés **n'ont plus de champ d'énergie** (ni dans « + Ajouter un dérivé », ni dans « Modifier la liste », ni dans une colonne du tableau commun) ; les valeurs qui y avaient été saisies restent en base mais ne servent plus. C'est l'application (`BIBAROOM.md`) et la vue `consumption_events` (`DATABASE.md`) qui appliquent la règle.
- **Suppression** : annonce d'abord le nombre de produits concernés, puis retire le dérivé de ces produits et de la liste (ou le masque, s'il vient de la liste de départ), en une seule opération (`count_drinks_with_derivative`, `delete_derivative`, voir `DATABASE.md`). Ces fonctions ne touchent que les listes de dérivés (`beer_derivative`, depuis le 2026-11-06 `spirit_derivative` et depuis le 2026-11-07 `tea_derivative`).
- **Colonnes et fonctions** : voir `DATABASE.md`. **Ordre de mise en ligne** : la base d'abord (fait le 2026-11-06), le déploiement de la gestion ensuite ; sans les colonnes, l'enregistrement d'une fiche bière échoue (la clé `derivatives` est envoyée à l'enregistrement de toute fiche bière, cidre, vin ou spiritueux, avec `[]` quand le produit n'est pas une bière).
- **Non vérifié** : un enregistrement réel d'une fiche sur la base de production (le déclencheur `protect_sensitive_fields` de `drinks_directory` n'a pas été lu) ; seul un essai après déploiement le dira.
- **Statistiques (décidé le 2026-11-06, base prête)** : seul le produit de base compte ; le dérivé ne change que les calories et, côté statistiques, n'apparaît que dans Mes Statistiques ; sur le verre lui-même il s'écrit « Jupiler · Mazout » (ticket, listes de verres) ou s'affiche en pastille grisée (journal BibaSolo) (voir `DATABASE.md` et `PROFILE.md`).
- **Prix (décidé le 2026-11-06)** : un dérivé garde le prix du produit de base, selon le volume ; la gestion n'a donc pas de prix à saisir par dérivé.
- **Pas encore décidé** : la composition de chaque dérivé (ex. « pils + cola », champ non construit).

### Listes modifiables de la fiche produit (arômes & saveurs, accords, moment, verre, caractéristiques)

Table `custom_list_items`, **commune à plusieurs listes** : la colonne `list_key` dit de quelle liste il s'agit, la clé primaire est `(list_key, code)` (« dessert » peut donc exister comme accord et comme moment sans conflit). Même modèle que les styles : une ligne est soit un élément **ajouté à la main** (code préfixé `perso_`), soit une **modification d'un élément de la liste figée** du code (même code : nouveau nom, nouveau groupe, ou masqué = supprimé, colonne `hidden`). Nom unique parmi les éléments visibles **d'une même liste** (casse et espaces ignorés), une seule colonne de libellé `fr`, colonne `group_title` vide pour une liste sans groupes. Lecture publique, écriture réservée aux cinq rôles du personnel.

Dans la fiche produit bière / cidre (Niveau 2 → Arômes & saveurs), « Modifier la liste » permet de renommer, de changer de groupe ou de supprimer n'importe quel arôme, y compris ceux de la liste figée ; « + Ajouter un arôme » en crée un nouveau. La suppression annonce d'abord le nombre de produits concernés, puis retire l'arôme de ces produits et de la liste en une seule opération. Deux fonctions génériques, réservées au personnel : `count_drinks_with_list_item(p_list, p_code)` et `delete_list_item(p_list, p_code, p_fr, p_group_title)`. Elles connaissent cinq listes : `flavor_note` (arômes & saveurs, colonne `flavor_notes`, plusieurs choix par produit), `food_pairing` (accords alimentaires, `food_pairings`, plusieurs choix), `occasion` (moment / occasion, colonne `occasion`, un seul choix) `recommended_glass` (verre recommandé, colonne `recommended_glass`, un seul choix) et `characteristic` (caractéristiques & labels, colonne `characteristics`, plusieurs choix). Pour une liste à plusieurs choix, l'élément supprimé est retiré du tableau du produit ; pour une liste à un seul choix, le champ est vidé. Les cinq listes sont branchées dans la fiche (Niveau 2 des bières et cidres) : les arômes dans « Arômes & saveurs », les accords, le moment et le verre dans « Service & consommation », les caractéristiques dans « Caractéristiques & labels ».

Dans « Service & consommation », ces trois listes n'ont pas de groupes (le panneau de modification n'a donc pas de choix de groupe, et `group_title` reste vide) : les **accords alimentaires** sont des étiquettes à plusieurs choix (on touche pour cocher ou décocher), le **moment / occasion** et le **verre recommandé** sont des listes déroulantes à un seul choix, avec une entrée vide « — ». Sous chaque champ, « + Ajouter un accord / un moment / un verre » crée l'élément et le choisit aussitôt pour ce produit (pour une liste déroulante, il remplace le choix en cours), et « Modifier la liste » montre les éléments en étiquettes en pointillés : en toucher une ouvre le panneau pour la renommer ou la supprimer, sans rien (dé)sélectionner pour le produit. Les modifications de chaque liste sont lues à l'ouverture de la section. Supprimer un élément annonce le nombre de produits concernés, puis le retire de la liste et de ces produits (accords : retiré du tableau ; moment et verre : champ vidé, affiché « — »). La fiche d'un produit dont le verre n'a jamais été renseigné (valeur absente en base) et celle d'un nouveau produit commencent sur « Pinte » ; un verre vidé reste vide (avant ce changement, un champ vide se réaffichait « Pinte »). Une valeur que la liste ne contient plus (élément supprimé, encore porté par un produit) s'affiche « code (inconnu) » plutôt que de disparaître. Limite connue : si « Pinte » est supprimé, un nouveau produit démarre quand même sur son code (affiché « pinte (inconnu) »).

**Caractéristiques & labels (Niveau 2, bières et cidres).** Les sept anciennes cases à cocher (sans alcool, faible en alcool, sans gluten, gluten réduit, bio, sans sucres ajoutés, sans lactose) sont devenues une liste d'étiquettes à plusieurs choix, sans groupes, comme les accords : « + Ajouter une caractéristique » crée et choisit aussitôt, « Modifier la liste » renomme ou supprime n'importe laquelle, y compris celles de départ. La suppression annonce le nombre de produits concernés, puis retire la caractéristique de ces produits et de la liste. Le produit porte la liste de ses caractéristiques dans `drinks_directory.characteristics` (des codes ; ceux de départ reprennent le nom des anciennes cases : `alcohol_free`, `low_alcohol`, `gluten_free`, `gluten_reduced`, `bio`, `sugar_free`, `lactose_free`). « Vegan » (liste déroulante) et « Labels / certifications » (étiquettes libres) ne changent pas.

**L'app publique lit peu de chose ici** : les cases `gluten_free` et `bio` (annuaire, icônes, filtres « sans gluten » et « bio »), et, depuis le 2026-10-30, la liste `characteristics` d'un produit pour un seul code, `perso_authentic_trappist_product_atp` (label « Authentic Trappist Product (ATP) » : grande icône sur la fiche produit). Un déclencheur de la base garde la liste et ces deux cases d'accord dans les deux sens (une case changée met la liste à jour ; une liste modifiée met les cases à jour, et la liste fait foi si les deux changent en même temps). Conséquences à connaître : **supprimer « Sans gluten » ou « Bio » depuis la plateforme les retire de tous les produits dans l'app** (icône et filtre ; la confirmation de suppression l'annonce) ; **supprimer le label ATP** retire de même son icône de la fiche de tous les produits (la confirmation l'annonce aussi) ; **renommer** une caractéristique ne change que la plateforme de gestion (l'app garde ses propres textes et reconnaît toujours le même code). La plateforme n'écrit plus que la liste et ces deux cases. Les cinq autres anciennes cases (sans alcool, faible en alcool, gluten réduit, sans sucres ajoutés, sans lactose) ont été **retirées de la table le 2026-10-27** : ces caractéristiques ne vivent plus que dans la liste de chaque produit, sans rien perdre.

Dans la liste figée des arômes, trois codes figuraient dans deux groupes à la fois (`banane`, `epice`, `poivre`). Comme un code ne peut avoir qu'une place une fois la liste modifiable, la gestion ne garde que la première (Banane dans « Fruits & agrumes », Épicé et Poivré dans « Houblon, végétal & floral ») : 84 arômes affichés au lieu de 87 entrées. Un élément rangé dans un groupe qui n'existe plus apparaît dans « Autres arômes ». Un arôme de la liste figée supprimé est **masqué**, pas effacé ; un nom supprimé peut être ajouté de nouveau (nouveau code `perso_…`).

Script : `listes-modifiables` (la table, ses deux règles d'accès et les deux fonctions), puis `caracteristiques-1-liste-modifiable` (colonne `characteristics`, reprise des cases déjà cochées sans bruit dans l'historique, déclencheur de synchronisation, et nouvelle version des deux fonctions qui connaît la liste `characteristic` ; retour arrière : `caracteristiques-1-retour-arriere`). **L'app publique ne lit pas cette table** : elle n'affiche ni les arômes, ni les accords, ni le moment, ni le verre d'un produit.

### Listes modifiables de la fiche lieu (paiement, types d'établissement, aménités)

Trois listes de la fiche lieu se gèrent comme celles de la fiche produit, depuis la plateforme de gestion : « Paiement → Moyens de paiement acceptés » (clé `payment_method`, colonne `accepted_payment_methods`), « Établissement → Type » (`venue_type`, colonne `venue_types`) et « Établissement → Aménités » (`amenity`, colonne `amenities`). Elles utilisent la même table `custom_list_items` (mêmes règles : élément ajouté à la main avec un code `perso_…`, ou modification d'un élément de départ : nouveau nom, ou masqué = supprimé ; lecture publique, écriture réservée aux cinq rôles du personnel). Les listes de départ sont celles du code : 20 moyens de paiement (« Bancontact » y a été ajouté, car 23 lieux le portaient déjà sans qu'il figure dans la liste), 43 types d'établissement et 18 aménités. Aucune de ces listes n'a de groupes.

Sous chaque champ : « + Ajouter … » crée l'élément et le coche aussitôt pour le lieu ; « Modifier la liste » montre les éléments en étiquettes en pointillés, et en toucher un ouvre son panneau : **renommer**, **déplacer** (« ↑ Monter » / « ↓ Descendre », avec la place actuelle) ou **supprimer**. En mode modification, rien n'est (dé)coché pour le lieu. La suppression annonce d'abord le nombre de **lieux** concernés, puis retire l'élément de ces lieux et de la liste en une seule opération (fonctions `count_venues_with_list_item(p_list, p_code)` et `delete_venue_list_item(p_list, p_code, p_fr, p_group_title)`, réservées au personnel ; `count_drinks_with_list_item` et `delete_list_item`, pour les produits, ne changent pas).

**L'ordre d'affichage** est enregistré dans la table `custom_list_order` (`list_key`, `codes` : la suite complète des codes dans l'ordre voulu, `updated_at` ; une ligne par liste ; lecture publique, écriture réservée au personnel). Chaque déplacement enregistre aussitôt l'ordre complet, indépendamment du bouton « Enregistrer » de la fiche du lieu. Un élément absent de l'ordre (ajouté depuis) s'affiche à la fin ; un code qui n'existe plus est ignoré ; supprimer un élément le retire aussi de l'ordre. Sans ordre enregistré, la liste garde son ordre de départ. Les listes de la fiche produit n'ont pas d'ordre modifiable, **sauf les listes de styles** (voir « Ordre des styles » plus haut).

**Aménités.** Les 18 anciennes cases à cocher (`has_wifi`, `has_terrace`, `wheelchair_accessible`, `can_dance`…) restent des colonnes de `public_venues`, mais le lieu porte maintenant la liste de ses aménités dans `public_venues.amenities` (jsonb, tableau de codes, défaut `[]`, non nulle ; une règle de contrôle impose que ce soit un tableau). Un déclencheur avant insertion et modification (`trg_venues_amenities_sync`) garde la liste et les 18 cases d'accord, dans les deux sens, sur le même modèle que les caractéristiques des produits : si seules des cases changent (c'est ce qu'écrivaient les anciennes versions de l'app), la liste suit ; si la liste change (plateforme de gestion), elle fait foi et les 18 cases suivent, même si une case est envoyée en même temps. La plateforme de gestion n'écrit plus que `amenities`. Les types d'établissement et les moyens de paiement étaient déjà des listes (colonnes jsonb) : aucune conversion. La colonne texte `venue_type` (un seul type) n'est pas touchée.

**Ce que l'app publique en lit.** Deux endroits de l'app lisent ces listes (tables `custom_list_items` et `custom_list_order`, lecture publique), une seule fois par session :

- les **noms des types d'établissement** : puces de la fiche d'un lieu et aperçus de partage des liens `bibamus.app/@nom` (fonction `api/at.js`, qui ne laisse que 1,5 s à cette lecture et garde sinon les noms de départ : ni une panne ni une lenteur ne bloquent un aperçu). Un type renommé ou ajouté dans la plateforme de gestion apparaît donc sous son nouveau nom. Un type ajouté à la main dont le nom n'est pas encore chargé n'est jamais montré sous son code technique (`perso_…`) ;

### Fiche producteur : adresse et listes modifiables (type, profil)

**Adresse** (fiche d'un producteur, section « Adresse ») : le **pays** vient en premier (liste déroulante, largeur limitée), puis **code postal** et **commune** sur une ligne (avec Geoapify configuré, les deux champs d'autocomplétion habituels ; sinon deux champs libres), puis **Rue / Place / Avenue**, **N°** et **Section / Village** sur une ligne ; latitude, longitude et géocodage ne changent pas. « Village » devient « Section / Village » (et le champ libre de repli, sans Geoapify, s'appelle « Commune » comme l'autocomplétion) : seuls les libellés changent, les colonnes (`street_name`, `street_number`, `postal_code`, `city`, `village`, `country`) sont les mêmes.

**Type et profil du producteur.** Les sections « Type de producteur » et « Profil du producteur » deviennent des listes modifiables, comme celles de la fiche lieu : clé `producer_type` (colonne `breweries_directory.producer_types`) et clé `producer_profile` (colonne `producer_profiles`). ### Liens des réseaux sociaux (fiches marque et producteur) (2026-11-10)

Dans la section « Coordonnées » d'une fiche **marque** (`BrandDetailPanel`) et d'une fiche **producteur** (`BreweryDetailPanel`), chaque réseau est un champ à **début pré-rempli** (`SocialLinkField`) : un bandeau montre le début fixe de l'adresse, et le champ en dessous reçoit seulement l'identifiant ; la valeur enregistrée est l'adresse complète (début + identifiant), ou vide si le champ est vidé. Réseaux d'une marque : Facebook, Instagram, TikTok, Snapchat, YouTube ; un producteur a en plus WhatsApp et LinkedIn. Débuts pré-remplis : `https://www.facebook.com/`, `https://www.instagram.com/`, `https://www.tiktok.com/@`, `https://www.snapchat.com/add/`, `https://www.linkedin.com/company/` (producteur), `https://wa.me/` (producteur) et, pour **YouTube**, `https://www.youtube.com/channel/` : on saisit l'identifiant de la chaîne (`UC…`) et le lien enregistré est `https://www.youtube.com/channel/<identifiant>`. Décision du 2026-11-10 (« le "@" n'a pas lieu d'être ») : le début était `https://www.youtube.com/@`. Ce changement de début ne modifie pas les liens déjà enregistrés : les **37** liens « `…/@UC…` » (identifiant de chaîne après le « @ », que YouTube n'ouvre pas) ont été corrigés une fois pour toutes par script le 2026-11-10 (voir `docs/DATABASE.md`) ; les 45 liens `youtube.com/@nom` (vrais noms de chaîne) restent valides. Un lien qui ne commence pas par le début pré-rempli (par exemple `https://www.youtube.com/@nom`) s'affiche en entier dans le champ, et il faut vider le champ avant de saisir un identifiant, sinon le début est ajouté devant. L'app ne fait que lire ces colonnes (`youtube_url` des tables `brands_directory` et `breweries_directory`) et affiche le lien tel qu'il a été saisi.
