## Principe général

Plateforme orientée ordinateur, séparée de l'app principale, pour encoder et vérifier les fiches (établissements, produits, marques, producteurs) plus vite que sur mobile, et pour piloter l'app (modération, drapeaux de fonctionnalités, discussion d'équipe). Dépôt GitHub distinct (`VaziooMedia/Bibamus-Management`), annoncée sur `admin.bibamus.app` **(dépôt admin)**.

Les indices d'un **même backend Supabase** que `bibamus-web` sont concordants — scripts « plateforme de gestion » placés dans les migrations communes (`ai-proposals-rls`, `styles-personnalises`, `schema-admin-chat*`), mêmes noms de fonctions dans la couche de données copiée — mais la preuve définitive (l'URL du projet) n'est pas lisible dans ce dépôt.

## Ce que `bibamus-web` contient de la plateforme (copies orphelines)

`bibamus-web` embarque des copies de composants d'administration **jamais importées depuis `App.jsx`** : `UserDetailPanel`, `VenuesScreen`, `DrinksScreen`, `VenueDetailPanel`, `DrinkDetailPanel`, `BreweryDetailPanel`, `BrandDetailPanel`, `SimpleEntityPanel`, `DataTable`, `ServerDataTable`, `DataBaseOverviewScreen`, `OpeningHoursEditor`, `GooglePlaceLinker`. Elles importent des fonctions **absentes** de `sharedDirectories.js` (`createAppUser`, `updateAppUserProfile`, `deleteAppUser`, `mergeEntities`, `searchGooglePlaceMatches`, `linkGooglePlace`, `unlinkGooglePlace`, `setNoGooglePresence`). Conséquence : une preuve trouvée dans ces copies **ne prouve pas** l'état du dépôt de gestion, dont elles sont des versions plus anciennes ou partielles.

Seuls `ImportDataScreen`, `BreweriesAdminScreen`, `BrandsAdminScreen` et une ligne « admin » dans `MinorScreens` sont réellement atteignables dans l'app, pour les comptes administrateurs.

## Gestion des utilisateurs

La gestion des utilisateurs **existe** (la version précédente de ce document, comme `DATABASE.md`, la disait pour l'un « construite », pour l'autre « non encore construite »). Ce que montre la copie de `UserDetailPanel` :

- Création et édition d'un compte : prénom, nom, surnom, date de naissance, pays, commune. **Nom d'utilisateur (@nom)** : voir le point suivant (la base refuse l'écriture directe de ce champ, y compris depuis cette plateforme : voir `DATABASE.md`). La commune est obligatoire (validation bloquante), comme pour l'enregistrement du profil dans l'app ; à l'inscription dans l'app, seul le pays est demandé.
- **Nom d'utilisateur (@nom) : comptes, lieux, marques et producteurs** (livré le 2026-10-24 ; lu dans le dépôt de gestion à la livraison, **(dépôt admin)** : non revérifié depuis) : une section repliable « Nom d'utilisateur » (repliée au départ, même en-tête que les autres sections de chaque fiche), visible seulement pour `admin` et `super_admin` (le rôle est transmis aux fiches par `MyRoleContext`) et seulement sur une fiche **déjà créée** ; dans la fiche d'un compte, avant « Informations » ; dans celles d'un lieu, d'une marque et d'un producteur, juste après « Dénomination » (composant `UsernameAdminField`). Elle relit le nom actuel dans la base à chaque ouverture, vérifie le nouveau nom pendant la frappe (`admin_check_username`, différée de 0,4 s), demande une confirmation (« Remplacer @ancien par @nouveau »), puis l'applique par `admin_set_username`. Sans limite de changements ; un nom réservé est permis, et changer seulement la casse aussi ; la forme, un nom déjà pris et le nom identique au nom actuel sont refusés, avec la phrase renvoyée par le serveur (la plateforme n'en invente aucune). Un changement marque le nom comme « changé » : un compte dont le nom a été changé par l'équipe ne peut plus le changer lui-même (la confirmation le dit pour un compte jamais changé). Les écritures habituelles de ces fiches (enregistrer, créer) n'envoient jamais `username`. Le changement par les gérants de fiches, depuis la plateforme Business, n'est pas construit. Voir `DATABASE.md`.
- `CityAutocomplete` pour la commune. La copie de `bibamus-web` lit `CITIES_BY_COUNTRY[country]` **sans conversion** ; la conversion code pays interne ↔ libellé que décrivait l'ancienne version n'existe que, si elle existe, dans la version du dépôt de gestion **(dépôt admin)**. Le panneau passe un code interne (`COUNTRIES` y est un tableau `{ code, fr }`, alors que dans `bibamus-web` c'est un tableau de chaînes) : les deux `constants.js` diffèrent.
- Attribution d'une `app_language` (`fr`, `nl`, `en`, `de`) — voir `MULTILINGUAL.md`.
- La création appelle `createAppUser(...)` ; la fonction Edge `admin-create-user` citée par l'ancienne version n'est **dans aucun fichier lu** **(dépôt admin)**.
- Statut administrateur dans l'app : automatique, déduit du rôle (voir `PROFILE.md`).

## Rôles

Les règles d'accès des scripts livrés et la fonction Edge d'IA admettent `editor`, `super_editor`, `moderator`, `admin`, `super_admin` ; les Stories officielles sont réservées à `admin` et `super_admin` ; dans l'app, `isAdmin` = `admin` ou `super_admin`. Le zip montre la version **admin** de `DrinkDetailPanel.jsx` (≈ 99 Ko, contre ≈ 65 Ko pour la copie de `bibamus-web`) et `SelectedStyleChips.jsx`. Les imports visibles décrivent ce que fait le panneau produit :

- **fusion de doublons** (`mergeEntities`, qui appelle `merge_entities`, réservé aux administrateurs) ;

- arômes & saveurs (Niveau 2) : `FlavorNotesPicker` → `GroupedListPicker` (accordéon, `ListItemAdder`, mode « Modifier la liste » avec `ListItemManagePanel`) ; « Service & consommation » (Niveau 2) : `FlatListField` → `FlatListEditor` (listes sans groupes : accords alimentaires, moment / occasion, verre recommandé, avec les mêmes `ListItemAdder` et `ListItemManagePanel`) ; « Caractéristiques & labels » (Niveau 2) : le même `FlatListField` en étiquettes, pour la liste des caractéristiques ; **listes modifiables** (`useCustomListItems`, `loadCustomListItems`, `createCustomListItem`, `saveCustomListItem`, `countDrinksWithListItem`, `deleteCustomListItem`) ;
- noms alternatifs et traductions (`AlternateNamesFields`, voir `MULTILINGUAL.md`).

À l'exception de `SelectedStyleChips`, aucun de ces composants importés n'est dans le zip.

### Propositions de l'IA (`ai_proposals`)

- Table `ai_proposals` (scripts `ai-proposals`, `ai-proposals-rls`, `fix-entity-id-type` : `entity_id` en texte). **Rien n'est jamais écrit automatiquement dans une fiche** : l'IA propose, un administrateur valide.
- Fonction Edge `ai-complete-entity` : réservée aux cinq rôles du personnel (contrôle du jeton et du rôle), appelle OpenAI avec recherche web, n'accepte que `entityType = "drink"`. Champs complétables : styles, année de lancement, région d'origine, nom alternatif, IBU, couleur EBC.
- Le service OpenAI reçoit donc des noms de produits ; le service de lecture d'étiquettes (`read-label`, côté app) lui envoie en plus des photos d'étiquettes.

### Styles personnalisés

Table `custom_beer_cider_styles` : une ligne est soit un style **ajouté à la main** (code préfixé `perso_`), soit une **modification d'un style de la liste figée** du code (même code que lui : nouveau nom, nouveau groupe, ou masqué = supprimé, colonne `hidden`). Nom unique parmi les styles visibles (casse et espaces ignorés), une seule colonne de libellé `fr`. Lecture publique, écriture réservée aux cinq rôles du personnel.

Dans la fiche produit bière / cidre (Niveau 1 → Style(s)), « Modifier la liste » permet de renommer, de changer de groupe ou de supprimer n'importe quel style, y compris ceux de la liste figée. La suppression annonce d'abord le nombre de produits concernés, puis retire le style de ces produits et de la liste en une seule opération (fonctions `count_drinks_with_beer_cider_style` et `delete_beer_cider_style`, réservées au personnel). Un style de la liste figée supprimé est **masqué**, pas effacé (il vit dans le code) ; un nom supprimé peut être ajouté de nouveau (nouveau code `perso_…`). Un style rangé dans un groupe qui n'existe plus apparaît dans « Autres styles ».

Scripts : `styles-personnalises` (la table), `styles-modifier-supprimer` (colonne `hidden` et deux fonctions), puis `styles-regle-des-codes` (retire la règle « code préfixé `perso_` », incompatible avec la modification d'un style de la liste figée). L'app publique lit la table une fois par session et affiche le nom enregistré en base avant le nom figé (`registerCustomStyleLabels`).

### Listes modifiables de la fiche produit (arômes & saveurs, accords, moment, verre, caractéristiques)

Table `custom_list_items`, **commune à plusieurs listes** : la colonne `list_key` dit de quelle liste il s'agit, la clé primaire est `(list_key, code)` (« dessert » peut donc exister comme accord et comme moment sans conflit). Même modèle que les styles : une ligne est soit un élément **ajouté à la main** (code préfixé `perso_`), soit une **modification d'un élément de la liste figée** du code (même code : nouveau nom, nouveau groupe, ou masqué = supprimé, colonne `hidden`). Nom unique parmi les éléments visibles **d'une même liste** (casse et espaces ignorés), une seule colonne de libellé `fr`, colonne `group_title` vide pour une liste sans groupes. Lecture publique, écriture réservée aux cinq rôles du personnel.

Dans la fiche produit bière / cidre (Niveau 2 → Arômes & saveurs), « Modifier la liste » permet de renommer, de changer de groupe ou de supprimer n'importe quel arôme, y compris ceux de la liste figée ; « + Ajouter un arôme » en crée un nouveau. La suppression annonce d'abord le nombre de produits concernés, puis retire l'arôme de ces produits et de la liste en une seule opération. Deux fonctions génériques, réservées au personnel : `count_drinks_with_list_item(p_list, p_code)` et `delete_list_item(p_list, p_code, p_fr, p_group_title)`. Elles connaissent cinq listes : `flavor_note` (arômes & saveurs, colonne `flavor_notes`, plusieurs choix par produit), `food_pairing` (accords alimentaires, `food_pairings`, plusieurs choix), `occasion` (moment / occasion, colonne `occasion`, un seul choix) `recommended_glass` (verre recommandé, colonne `recommended_glass`, un seul choix) et `characteristic` (caractéristiques & labels, colonne `characteristics`, plusieurs choix). Pour une liste à plusieurs choix, l'élément supprimé est retiré du tableau du produit ; pour une liste à un seul choix, le champ est vidé. Les cinq listes sont branchées dans la fiche (Niveau 2 des bières et cidres) : les arômes dans « Arômes & saveurs », les accords, le moment et le verre dans « Service & consommation », les caractéristiques dans « Caractéristiques & labels ».

Dans « Service & consommation », ces trois listes n'ont pas de groupes (le panneau de modification n'a donc pas de choix de groupe, et `group_title` reste vide) : les **accords alimentaires** sont des étiquettes à plusieurs choix (on touche pour cocher ou décocher), le **moment / occasion** et le **verre recommandé** sont des listes déroulantes à un seul choix, avec une entrée vide « — ». Sous chaque champ, « + Ajouter un accord / un moment / un verre » crée l'élément et le choisit aussitôt pour ce produit (pour une liste déroulante, il remplace le choix en cours), et « Modifier la liste » montre les éléments en étiquettes en pointillés : en toucher une ouvre le panneau pour la renommer ou la supprimer, sans rien (dé)sélectionner pour le produit. Les modifications de chaque liste sont lues à l'ouverture de la section. Supprimer un élément annonce le nombre de produits concernés, puis le retire de la liste et de ces produits (accords : retiré du tableau ; moment et verre : champ vidé, affiché « — »). La fiche d'un produit dont le verre n'a jamais été renseigné (valeur absente en base) et celle d'un nouveau produit commencent sur « Pinte » ; un verre vidé reste vide (avant ce changement, un champ vide se réaffichait « Pinte »). Une valeur que la liste ne contient plus (élément supprimé, encore porté par un produit) s'affiche « code (inconnu) » plutôt que de disparaître. Limite connue : si « Pinte » est supprimé, un nouveau produit démarre quand même sur son code (affiché « pinte (inconnu) »).

**Caractéristiques & labels (Niveau 2).** Les sept anciennes cases à cocher (sans alcool, faible en alcool, sans gluten, gluten réduit, bio, sans sucres ajoutés, sans lactose) sont devenues une liste d'étiquettes à plusieurs choix, sans groupes, comme les accords : « + Ajouter une caractéristique » crée et choisit aussitôt, « Modifier la liste » renomme ou supprime n'importe laquelle, y compris celles de départ. La suppression annonce le nombre de produits concernés, puis retire la caractéristique de ces produits et de la liste. Le produit porte la liste de ses caractéristiques dans `drinks_directory.characteristics` (des codes ; ceux de départ reprennent le nom des anciennes cases : `alcohol_free`, `low_alcohol`, `gluten_free`, `gluten_reduced`, `bio`, `sugar_free`, `lactose_free`). « Vegan » (liste déroulante) et « Labels / certifications » (étiquettes libres) ne changent pas.

**L'app publique n'est pas touchée** : elle lit toujours les cases `gluten_free` et `bio` (annuaire, icônes, filtres « sans gluten » et « bio »). Un déclencheur de la base garde la liste et ces deux cases d'accord dans les deux sens (une case changée met la liste à jour ; une liste modifiée met les cases à jour, et la liste fait foi si les deux changent en même temps). Conséquences à connaître : **supprimer « Sans gluten » ou « Bio » depuis la plateforme les retire de tous les produits dans l'app** (icône et filtre ; la confirmation de suppression l'annonce) ; **renommer** une caractéristique ne change que la plateforme de gestion (l'app garde ses propres textes). La plateforme n'écrit plus que la liste et ces deux cases. Les cinq autres anciennes cases (sans alcool, faible en alcool, gluten réduit, sans sucres ajoutés, sans lactose) ont été **retirées de la table le 2026-10-27** : ces caractéristiques ne vivent plus que dans la liste de chaque produit, sans rien perdre.

Dans la liste figée des arômes, trois codes figuraient dans deux groupes à la fois (`banane`, `epice`, `poivre`). Comme un code ne peut avoir qu'une place une fois la liste modifiable, la gestion ne garde que la première (Banane dans « Fruits & agrumes », Épicé et Poivré dans « Houblon, végétal & floral ») : 84 arômes affichés au lieu de 87 entrées. Un élément rangé dans un groupe qui n'existe plus apparaît dans « Autres arômes ». Un arôme de la liste figée supprimé est **masqué**, pas effacé ; un nom supprimé peut être ajouté de nouveau (nouveau code `perso_…`).

Script : `listes-modifiables` (la table, ses deux règles d'accès et les deux fonctions), puis `caracteristiques-1-liste-modifiable` (colonne `characteristics`, reprise des cases déjà cochées sans bruit dans l'historique, déclencheur de synchronisation, et nouvelle version des deux fonctions qui connaît la liste `characteristic` ; retour arrière : `caracteristiques-1-retour-arriere`). **L'app publique ne lit pas cette table** : elle n'affiche ni les arômes, ni les accords, ni le moment, ni le verre d'un produit.

### Listes modifiables de la fiche lieu (paiement, types d'établissement, aménités)

Trois listes de la fiche lieu se gèrent comme celles de la fiche produit, depuis la plateforme de gestion : « Paiement → Moyens de paiement acceptés » (clé `payment_method`, colonne `accepted_payment_methods`), « Établissement → Type » (`venue_type`, colonne `venue_types`) et « Établissement → Aménités » (`amenity`, colonne `amenities`). Elles utilisent la même table `custom_list_items` (mêmes règles : élément ajouté à la main avec un code `perso_…`, ou modification d'un élément de départ : nouveau nom, ou masqué = supprimé ; lecture publique, écriture réservée aux cinq rôles du personnel). Les listes de départ sont celles du code : 20 moyens de paiement (« Bancontact » y a été ajouté, car 23 lieux le portaient déjà sans qu'il figure dans la liste), 43 types d'établissement et 18 aménités. Aucune de ces listes n'a de groupes.

Sous chaque champ : « + Ajouter … » crée l'élément et le coche aussitôt pour le lieu ; « Modifier la liste » montre les éléments en étiquettes en pointillés, et en toucher un ouvre son panneau : **renommer**, **déplacer** (« ↑ Monter » / « ↓ Descendre », avec la place actuelle) ou **supprimer**. En mode modification, rien n'est (dé)coché pour le lieu. La suppression annonce d'abord le nombre de **lieux** concernés, puis retire l'élément de ces lieux et de la liste en une seule opération (fonctions `count_venues_with_list_item(p_list, p_code)` et `delete_venue_list_item(p_list, p_code, p_fr, p_group_title)`, réservées au personnel ; `count_drinks_with_list_item` et `delete_list_item`, pour les produits, ne changent pas).

**L'ordre d'affichage** est enregistré dans la table `custom_list_order` (`list_key`, `codes` : la suite complète des codes dans l'ordre voulu, `updated_at` ; une ligne par liste ; lecture publique, écriture réservée au personnel). Chaque déplacement enregistre aussitôt l'ordre complet, indépendamment du bouton « Enregistrer » de la fiche du lieu. Un élément absent de l'ordre (ajouté depuis) s'affiche à la fin ; un code qui n'existe plus est ignoré ; supprimer un élément le retire aussi de l'ordre. Sans ordre enregistré, la liste garde son ordre de départ. Les listes de la fiche produit n'ont pas d'ordre modifiable.

**Aménités.** Les 18 anciennes cases à cocher (`has_wifi`, `has_terrace`, `wheelchair_accessible`, `can_dance`…) restent des colonnes de `public_venues`, mais le lieu porte maintenant la liste de ses aménités dans `public_venues.amenities` (jsonb, tableau de codes, défaut `[]`, non nulle ; une règle de contrôle impose que ce soit un tableau). Un déclencheur avant insertion et modification (`trg_venues_amenities_sync`) garde la liste et les 18 cases d'accord, dans les deux sens, sur le même modèle que les caractéristiques des produits : si seules des cases changent (c'est ce qu'écrivaient les anciennes versions de l'app), la liste suit ; si la liste change (plateforme de gestion), elle fait foi et les 18 cases suivent, même si une case est envoyée en même temps. La plateforme de gestion n'écrit plus que `amenities`. Les types d'établissement et les moyens de paiement étaient déjà des listes (colonnes jsonb) : aucune conversion. La colonne texte `venue_type` (un seul type) n'est pas touchée.

**Ce que l'app publique en lit.** Deux endroits de l'app lisent ces listes (tables `custom_list_items` et `custom_list_order`, lecture publique), une seule fois par session :

- les **noms des types d'établissement** : puces de la fiche d'un lieu et aperçus de partage des liens `bibamus.app/@nom` (fonction `api/at.js`, qui ne laisse que 1,5 s à cette lecture et garde sinon les noms de départ : ni une panne ni une lenteur ne bloquent un aperçu). Un type renommé ou ajouté dans la plateforme de gestion apparaît donc sous son nouveau nom. Un type ajouté à la main dont le nom n'est pas encore chargé n'est jamais montré sous son code technique (`perso_…`) ;
- l'assistant **« Ajouter un lieu »** (pages « Type » et « Aménités ») : il propose les listes de la plateforme de gestion (noms, ordre, éléments ajoutés ; les éléments supprimés n'y figurent plus) et enregistre le choix sous forme de listes de codes (`venue_types`, `amenities`) ; le déclencheur remplit les 18 cases. Si la lecture échoue, l'assistant propose les listes de départ du code. Un choix supprimé depuis la gestion pendant la saisie n'est pas envoyé.

Ce que l'app ne lit toujours pas : sur la fiche d'un lieu, seules trois aménités s'affichent (WiFi gratuit, Accessible PMR, Possibilité de danser), par leurs cases ; renommer ou ajouter les autres ne change donc rien à la fiche. La statistique « Type de lieu préféré » (comparaison entre amis) affiche, elle aussi, le nom enregistré : l'app traduit le code rendu par la base (`get_bibax_stats_venues`) ; un code `perso_…` sans nom connu n'est jamais montré tel quel, et un nom déjà rendu par la base serait affiché tel quel. Le classement des types de lieux (`get_my_venue_type_ranking`) est chargé par l'écran des statistiques personnelles mais n'y est pas affiché. Les moyens de paiement ne sont pas affichés dans l'app. Conséquence à connaître : **supprimer un type de départ, ou l'aménité « WiFi gratuit », « Accessible PMR » ou « Possibilité de danser », les retire de tous les lieux dans l'app** (la confirmation de suppression l'annonce).

Mise en service : script `lieux-1-listes-modifiables` lancé le 2026-10-28 (table `custom_list_order`, les deux fonctions, colonne `amenities`, reprise des 18 cases déjà cochées sans bruit dans l'historique des modifications, déclencheur) ; résultat vérifié : 91 lieux dont 62 avec au moins une aménité, 0 incohérence entre la liste et les 18 cases, et un nombre de lieux par aménité identique à celui du relevé préalable. Retour arrière : `lieux-1-retour-arriere` (supprime déclencheur, fonctions, colonne, table d'ordre et les modifications de ces trois listes).

### Fiche producteur : adresse et listes modifiables (type, profil)

**Adresse** (fiche d'un producteur, section « Adresse ») : le **pays** vient en premier (liste déroulante, largeur limitée), puis **code postal** et **commune** sur une ligne (avec Geoapify configuré, les deux champs d'autocomplétion habituels ; sinon deux champs libres), puis **Rue / Place / Avenue**, **N°** et **Section / Village** sur une ligne ; latitude, longitude et géocodage ne changent pas. « Village » devient « Section / Village » (et le champ libre de repli, sans Geoapify, s'appelle « Commune » comme l'autocomplétion) : seuls les libellés changent, les colonnes (`street_name`, `street_number`, `postal_code`, `city`, `village`, `country`) sont les mêmes.

**Type et profil du producteur.** Les sections « Type de producteur » et « Profil du producteur » deviennent des listes modifiables, comme celles de la fiche lieu : clé `producer_type` (colonne `breweries_directory.producer_types`) et clé `producer_profile` (colonne `producer_profiles`). Les deux colonnes sont déjà des listes (jsonb, tableau de codes, défaut `[]`, vide autorisée) : aucune conversion. Elles utilisent les mêmes tables `custom_list_items` (élément ajouté à la main avec un code `perso_…`, ou modification d'un élément de départ : nouveau nom, ou masqué = supprimé) et `custom_list_order` (ordre d'affichage). Les listes de départ sont celles du code (`PRODUCER_TYPES` : 9 types, de Brasserie à Alimentaire ; `PRODUCER_PROFILES` : 10 profils, de Micro-producteur à Coopérative). Comme pour les lieux, les éléments se présentent en étiquettes à plusieurs choix ; « + Ajouter … » crée l'élément et le coche aussitôt pour le producteur, « Modifier la liste » permet de **renommer**, **déplacer** (« ↑ Monter » / « ↓ Descendre ») ou **supprimer**, et chaque déplacement enregistre aussitôt l'ordre complet, indépendamment du bouton « Enregistrer » de la fiche.

La suppression annonce d'abord le nombre de **producteurs** concernés, puis retire l'élément de ces producteurs et de l'ordre de sa liste, puis le supprime (élément ajouté) ou le masque (élément de départ), en une seule opération : fonctions `count_producers_with_list_item(p_list, p_code)` et `delete_producer_list_item(p_list, p_code, p_fr, p_group_title)`, réservées au personnel (les cinq rôles), qui connaissent les deux listes `producer_type` et `producer_profile` et refusent toute autre. Supprimer un **type de départ** affiche un avertissement (l'application Bibamus l'utilise sur les cartes publiques des producteurs) ; supprimer un profil n'en affiche pas, l'application n'affichant pas les profils. Dans le tableau des producteurs, les colonnes « Type » et « Profil du Producteur » montrent les noms de la gestion (élément renommé ou ajouté) ; les noms sont relus à l'ouverture de l'écran puis à la fermeture de chaque fiche.

**Ce que l'app publique en lit** (câblage du 2026-10-28, code seulement : aucun script SQL de plus). Deux endroits de l'app lisent ces listes (tables `custom_list_items` et `custom_list_order`, lecture publique), une seule fois par session et par groupe de listes ; les deux clés sont dans `src/producerLists.js`, la logique commune (nettoyage, fusion avec la liste de départ, ordre) dans `src/venueLists.js` :

- l'assistant **« Ajouter un producteur »** (pages « Type de producteur » et « Profil du producteur ») : il propose les listes de la plateforme de gestion (noms, ordre, éléments ajoutés ; les éléments supprimés n'y figurent plus) et enregistre le choix sous forme de listes de codes (`producer_types`, `producer_profiles`). Si la lecture échoue, l'assistant propose les listes de départ du code (`PRODUCER_TYPES`, `PRODUCER_PROFILES`, dans `constants.js`). Un choix supprimé depuis la gestion pendant la saisie n'est pas envoyé ;
- les **noms des types de producteur** sur les cartes de partage : aperçu des liens `bibamus.app/@nom` d'un producteur (fonction `api/at.js`, qui ne laisse que 1,5 s à cette lecture) et carte publique de l'app (2,5 s). Sans réponse à temps ou en cas de panne, les noms de départ sont gardés : ni une panne ni une lenteur ne bloquent un aperçu. Un type renommé ou ajouté dans la plateforme de gestion apparaît sous son nouveau nom ; un code `perso_…` dont le nom n'est pas connu n'est jamais montré sous son code technique. Les types de **marque** suivent le même principe (voir « Fiche marque : listes modifiables »).

Ce que l'app ne lit pas : les **profils** ne sont affichés nulle part dans l'app, et l'écran de la fiche d'un producteur ne montre aujourd'hui ni type ni profil. Sa construction côté app n'est **pas à l'ordre du jour** (décision du 2026-10-28 : on continue d'abord à peaufiner les fiches Produits, dont on reprendra un maximum d'éléments). L'ancienne copie `BreweryDetailPanel.jsx` (jamais importée, voir plus haut) garde les listes de départ : sans effet. Conséquence à connaître : **supprimer un type de départ le retire de tous les producteurs qui le portent, donc de leur carte publique**, et l'assistant « Ajouter un producteur » ne le propose plus.

Mise en service : script `producteurs-1-listes-modifiables` lancé le 2026-10-28 (les deux fonctions uniquement : aucune colonne, aucun déclencheur, aucune donnée de producteur n'est touchée) ; relevé préalable `producteurs-0-releve` (lecture seule) : 127 producteurs, aucun code hors des listes de départ, 3 producteurs sans type et 2 sans profil, aucune ligne ni aucun ordre déjà enregistré pour ces listes ; résultat vérifié après lancement : les deux fonctions en droits du propriétaire, refusées à anon, et un nombre de producteurs par type et par profil identique à celui du relevé. Retour arrière : `producteurs-1-retour-arriere` (supprime les deux fonctions et les modifications de ces deux listes, éléments et ordre ; la table d'ordre et les fonctions des lieux et des produits restent).

### Fiche marque : listes modifiables (classification, type de marque)

Les deux colonnes sont déjà des listes (jsonb, tableau de codes, défaut `[]`, vide autorisée) : aucune conversion. La colonne texte historique `classification` (au singulier) n'est pas touchée.
