# BIBAROOM — Documentation as-built

> Documente l'état réel du code tel qu'implémenté, pas un historique de conversation. À mettre à jour quand l'implémentation change.
> Dernière mise à jour : 2026-10-13. Vérifié contre le code de l'app (`src/`) et les scripts SQL / fonctions Edge livrés. La mention **(base)** signale ce qui ne se lit que dans Supabase : aucun script livré ne le contient (c'est le cas de la table `salons`, de ses règles d'accès et de la plupart des fonctions de salon), donc non revérifié.

## Principe général

Un BibaRoom est un salon partagé qui représente une sortie ou une soirée. Il se crée depuis **BibaGo** (`SessionHubScreen`, qui propose aussi BibaSolo et, grisé « Soon », BibArena) et se rejoint avec un code. Le code du salon fait office de clé d'accès : le client charge un salon avec son seul code, sans vérification d'appartenance. Les Stories de salon suivent le même principe.

Écran d'un salon (`SalonTabsScreen`) : **trois onglets** — Biba|Room (le tableau de bord, `EventDashboardScreen`), Biba|Pulse (fil du salon, construit à partir de l'état du salon, pas de `pulse_events` : les tournées, les **checks** faits dans le salon, et les arrivées et départs — voir « Drink Check ») et Biba|Ping (chat du salon). La barre des trois boutons est le composant partagé `PillTabs` (`src/components/PillTabs.jsx`), le même aspect que les fiches Produits et Lieux et que les BibaClub depuis le 2026-10-30 : pastilles rondes de même largeur, onglet actif plein vert fluo, **sans icônes**, avec **une ligne de séparation au-dessus et une en dessous**. Une pastille rouge à cheval sur la bordure compte les éléments non lus de Pulse et de Ping. La barre est construite une seule fois, dans `SalonTabsScreen`.

## Modes

Un salon est dans **un** des quatre modes ; les noms « ORBIS », « ARCA », « PARTES » et « LIBER » sont les noms **affichés** à l'utilisateur. Les identifiants internes sont ceux de `event.mode` :

| Nom affiché | Identifiant interne | Rôle |
|---|---|---|
| ORBIS | `tournees` | Chacun paie un tour à tour de rôle |
| ARCA | `cagnotte` | Pot commun |
| PARTES | `addition` | Répartition de la note |
| LIBER | `openbar` | Consommation libre, sans calcul de tournée (prix à 0) |

### BibaZERO

**BibaZERO n'est pas un mode** : c'est un **statut par participant**, qui se combine avec n'importe lequel des quatre modes (champ `event.bibaBob[code]` de l'état du salon : nom, tolérance `zero` ou `joker`, code PIN à 4 chiffres, joker utilisé, date d'activation). Il s'adresse à toute personne qui ne boit pas, quelle qu'en soit la raison. Dans le code, l'ancien nom « BibaBob » subsiste (`activateBibaBob`, `BibaBobModal`, champ `bibaBob`). Deux tolérances : « zéro » ou « avec 1 joker » (usage unique). Les boissons alcoolisées (> 0,5 % vol.) sont filtrées de la composition d'une tournée pour ce participant. Un rappel d'eau (**WaterAlert**) peut être réglé par salon. BibaZERO existe aussi **hors salon**, dans BibaSolo, enregistré sur le profil (voir `PROFILE.md`).

## Identifiants

- **Code de salon : 6 caractères**, alphabet restreint de 31 symboles (`23456789ABCDEFGHJKMNPQRSTUVWXYZ`, sans 0, 1, I, L, O). La saisie (`JoinSalonScreen`) filtre l'alphabet et limite à 6. Des commentaires périmés dans le code parlent encore de 4 caractères.
- **Code participant = code Bibax** (`myBibroCode`) : 6 caractères, lettres et chiffres, validés côté client ; la génération est dans la base **(base)**.
- Unicité du code de salon : testée (8 essais) par la création depuis le tableau de bord de salon ; **non testée** par `createEvent`, la création principale depuis BibaGo.

## Stockage et synchronisation

- Une ligne par salon dans la table `salons` : `code`, `data` (un seul bloc JSON), `updated_at`. **Tout** l'état du salon — participants, tournées, playlist, BibaZERO, notices, invitations — vit dans ce JSON ; il n'y a pas de table relationnelle par participant.
- Chaque modification réécrit **tout** le JSON : en cas de modifications simultanées depuis deux appareils, la dernière arrivée l'emporte. La synchronisation temps réel écoute les `UPDATE` de la ligne.
- La liste locale des salons (`bibamus-events`) est aussi gardée dans le navigateur.
- **Qui est dans le JSON** (relevé du 2026-10-23, structure seulement) : un participant est `{code, name, joinedAt}` — son `code` est le code Bibax du compte (`profiles.bibro_code`), **jamais** un identifiant de compte ; un ami de tournée est `{id, name, code, isSelf}`, avec `code` vide pour un invité sans compte. C'est ce qui permet de relier un salon à des comptes (voir `get_bibax_stats_social`, `BIBAX.md`).
- **Multi-appareil** : `get_my_active_salons(p_bibro_code)` (appelée au chargement puis toutes les 30 secondes) retrouve les salons où l'utilisateur figure dans le JSON des participants ; elle **ajoute** les salons absents de la liste locale, sans jamais mettre à jour un salon déjà connu.
- **Accès** : l'app ne lit ni n'écrit la table `salons` directement (`src/data/salons.js`). Elle passe par des fonctions serveur **(base)** : `get_salon(code)` (lecture, y compris pour rejoindre : le code reste le « mot de passe » du salon), `save_salon(code, data)` (création et mise à jour : réservée aux participants, à une personne qui se rajoute sans retirer personne, ou au créateur d'un nouveau salon), `decline_salon_invite(code)` (retire sa propre invitation en attente) et `get_club_round_buyers(club)` (statistiques de club, membres actifs seulement). La table elle-même est **fermée** (vérifié dans Supabase le 2026-10-09) : lecture directe réservée aux participants du salon (lus dans le JSON, `participants[].code`) et aux administrateurs, écriture directe réservée aux administrateurs, aucun droit pour les visiteurs **(base)** — voir `SECURITY.md`.

## Fonctionnement

- **Entrer dans un salon** : trois chemins — l'écran `JoinSalonScreen` (code ou **scan de QR code**), le champ de code du tableau de bord, et l'acceptation d'une **invitation** (notification envoyée à un Bibax). Deux chemins de création : `createEvent` (depuis BibaGo) et la transformation d'un événement local en salon. À la création par `createEvent`, les Bibax choisis dans « Participants » de `NewEventScreen` reçoivent une **vraie invitation** (notification `send_salon_invite` + push « t'invite à rejoindre… ») et figurent comme invitations en attente (`pendingBibaxInvites`), comme avec « Inviter un Bibax » du tableau de bord, au lieu d'un simple nom ajouté à la liste. Un événement solo (sans salon) garde le simple nom. Un échec d'envoi est silencieux ; l'hôte peut réinviter depuis le tableau de bord.
- **QR code** : affiché dans le salon (`QRCodeSVG`) et scanné par la caméra (`SalonQrScannerModal`).
- **Pause** : au niveau de l'événement entier (`paused`) et individuellement par participant.
- **Quitter, Safe** : « Quitter », puis un bouton « Safe » pour dire qu'on est bien arrivé ; notices système (`joined`, `left`, `safe`, les 10 dernières) et notification push « est bien arrivé(e) » aux autres participants, envoyée **avant** que l'on soit retiré de la liste des participants du salon (le serveur ne notifie que des personnes ayant un lien avec l'expéditeur) et attendue au plus 4 secondes.
- **Tournées** : composition d'un tour (`RoundComposeScreen`), ticket récapitulatif (`RoundTicketScreen` : « offert par » un lieu ou un tiers, règlement direct ou sur la note, total comptoir, propositions de pourboire), paiements partiels, cagnotte (`PotCard`), addition partagée (`SplitBillCard`), rotation du payeur.
- **Produit absent de la carte (BibAtlas, nouvelle commande)** : dans la composition d'une tournée (`RoundComposeScreen`), le champ « Chercher dans BibAtlas… » (écran des catégories) propose les produits du répertoire absents de la carte du lieu. Choisir un produit ouvre la fenêtre d'ajout : en haut, le **rond-profil du produit** (photo, sinon emoji, sinon bouteille) à gauche de son nom ; puis, sur **une seule ligne**, les blocs d'encodage — **Volume (cl.)** (84 px), **Prix (€)** ou **Jetons** (96 px) et **Type de service** (menu à la largeur de son texte, environ 104 px) —, champs de 46 px au texte centré ; puis la phrase « Ce produit rejoindra la carte de ce lieu » ; puis le bouton **« Ajouter »** et « Annuler ». Les espaces au-dessus des blocs, sous les blocs et sous la phrase sont tous de 24 px (constante `SHEET_GAP`) : la phrase sert de tampon, pour qu'un doigt qui règle une valeur (flèches des jetons) n'atteigne pas « Ajouter » par erreur. **Volume** : champ libre, chiffres seulement (virgule ou point acceptés, un seul séparateur, 6 caractères au plus), **pré-rempli avec le volume par défaut du produit** (`defaultVolumeCl`, « 33 », « 37,5 » ; vide, avec « 00 » en indication, s'il n'y en a pas) ; vide ou à 0, il est enregistré comme « volume non défini » (`volumeCl` null). **Type de service** : Non défini, Bouteille, Canette, On Tap, Au verre — mêmes choix, même ordre et mêmes libellés que « Next Drink » (`SERVING_MODE_OPTIONS`, `utils.js`) —, **pré-sélectionné avec le type de service par défaut de la fiche produit** (`defaultServingMode` ; absent ou inconnu → « Non défini », `defaultServingModeText`) ; le choix est rangé sur l'entrée de carte (`servingMode`, nettoyé par `safeServingMode`). Le bloc prix **suit la devise du salon** (`event.currency`) : en **euros**, « Prix (€) » est un champ vide (« 0,00 » en indication, virgule ou point, 7 caractères au plus), aucun prix par défaut ; en **jetons**, le bloc s'appelle « Jetons » (avec l'icône jeton), commence à **1** et se règle avec deux flèches (+1 en haut, −1 en bas, désactivée à 0 : jamais négatif) ou en tapant un nombre entier (3 chiffres au plus, plafond 999). En mode LIBER (bar ouvert) il n'y a pas de prix : seuls le volume et le type de service sont demandés et le prix est 0. Les champs sont remis à leur valeur de départ à chaque produit choisi. À la validation (`handleConfirmBibAtlasAdd`), `onAddBibAtlasProduct(produit, { volumeCl, price, servingMode })` rend le produit commandable : `price` est un nombre dans la devise du salon (jetons entiers ou euros) ; les fonctions de saisie sont dans `utils.js` (`defaultVolumeText`, `sanitizeDecimalText`, `sanitizeDigitsText`, `parsePositiveText`, `parsePriceText`, `parseTokensText`, `stepTokens`). Le produit est écrit dans la carte publique du lieu **et** dans la carte du salon avec ce même prix et ce même type de service : si la devise du salon n'est pas celle du lieu, la valeur saisie (jetons) arrive telle quelle dans la carte du lieu. La fenêtre « Next Drink » des salons @Home (`HomeServeSheet`) a ses propres champs, inchangés.
- **Salon @Home** (`event.isHome`, créé en mode LIBER sans lieu) : chez soi, pas de carte à télécharger ni de tournée. Le bouton « + Nouvelle tournée » devient **« Next Drink »** (il ouvre `HomeServeSheet`, la fenêtre intitulée **BibAtlas**) : on cherche un produit dans **BibAtlas** — en écrivant, ou avec l'icône IA de la barre de recherche, qui lit l'étiquette de la bouteille (avec BibaZERO actif, une boisson alcoolisée reconnue n'est pas proposée) —, on encode son volume dans un **champ libre** « Volume (cl.) » (nombre centré, virgule ou point, bloc étroit de 114 px comme dans BibaSolo ; facultatif) et, à côté, son **« Type de service »** (menu déroulant : Non défini, Bouteille, Canette, On Tap, Au verre — même ordre et mêmes libellés que le « Type de service par défaut » de la fiche produit côté Gestion). Les deux sont **pré-remplis avec les valeurs par défaut de la fiche produit** (`defaultVolumeCl`, `defaultServingMode` ; un type de service inconnu ou absent donne « Non défini ») et se corrigent avant « Me servir ». Le verre est ajouté **pour soi seulement** ; « + » reprend le même verre (même volume, même type de service), « − » retire le dernier. Dans la liste « Mes verres (n) » de BibAtlas, le type de service de chaque verre est écrit en petite pastille fine sous le nom et le volume (si le nom est trop long il se coupe par « … » : le volume et la pastille restent visibles). Les produits rejoignent la carte **du salon** (jamais celle d'un lieu), sans doublon par produit, volume **et type de service** (`buildHomeServe`) : le type de service est gardé sur l'entrée de carte (`servingMode`), donc le même produit au même volume mais servi autrement devient une autre entrée. Chaque verre est une entrée de `event.homeDrinks` — `{ id, code, name, drinkId, timestamp }` — rangée **par code de participant**, ce qui évite que les verres des uns écrasent ceux des autres dans le bloc JSON partagé. Le salon affiche **« Qui a bu quoi »** (par participant, du plus servi au moins servi ; sous chaque prénom, **un produit par ligne, précédé d'un tiret, avec la quantité « ×2 » alignée en bout de ligne** — sur le bord droit de la carte, comme « n verres » : « - Duvel 33 cl. … ×2 » ; **nom + volume tiennent toujours sur une seule ligne : si le nom est trop long, il est coupé par « … » et le volume reste entier** ; le **type de service** du verre (Bouteille, Canette, On Tap, Au verre) est écrit dessous, en **petite pastille fine** sur sa propre ligne — composant `ServiceTag`, rien si le produit n'en a pas ; le même produit au même volume mais servi autrement fait donc deux lignes) à la place de la liste des tournées, qui reste visible seulement dans un ancien salon @Home qui en contient déjà. « Ajouter une boisson hors tournée » est masqué, ainsi que tout ce qui n'a plus de sens sans carte ni tournée : le bouton **« Produits »** (tout passe par BibAtlas), le bloc **« Suggestion pour la prochaine tournée »**, et l'argent — la colonne « Dépensé(s) » et le détail « Sur la note / Déjà payé / Total » de « Mes statistiques » et de « Statistiques générales » (dans un salon @Home qui contenait déjà des tournées, la ligne « Tournées offertes · Bibax » reste). Les « VERRES » de « Statistiques générales » comptent aussi les verres pris en se servant. Sans le bouton « Produits », la rangée BibaMusic / ZERO / WaterAlert garde **ZERO et WaterAlert côte à côte, à droite** (un conteneur `display: flex` seulement chez soi ; ailleurs la rangée se répartit comme avant). Un participant en BibaZERO ne se voit proposer que des boissons sans alcool (le joker n'est pas géré ici). **WaterAlert** : le libellé « Toutes les X tournées » est conservé — à la maison il se lit « tous les X verres personnels » : la fenêtre de rappel s'affiche quand **moi** je me suis servi X verres depuis le dernier rappel (chacun compte les siens, rien n'est partagé) ; le mode « temps » est inchangé. La **notification** envoyée par le serveur (app fermée) reste liée aux vraies tournées : elle ne se déclenche donc pas à la maison. Chaque verre est aussi enregistré en statistiques (voir « Commandes enregistrées en base »).
- **Rond de profil du salon** (accueil BibaLive, en-tête du salon, en-tête BibaRoom) : la photo ou l'emoji du lieu lié s'il en a un. Sinon, un salon **@Home** affiche une **maison** et un salon **@Event** un **feu d'artifice** (pictos vert fluo `home-icon.svg` / `event-icon.svg`, 62 % du rond) à la place du monogramme Bibamus ; un salon sans lieu photo mais lié à un vrai lieu garde le monogramme (composant `SalonAvatar`).
- **Réglages de la session : changer de lieu** (`EventSettingsScreen`, enregistrement dans `App.jsx` via `withVenueChange`). Changer de lieu remplace la **carte du salon** par celle du nouveau lieu (vide pour @Home et @Event). La carte @Home — les produits pris avec « Next Drink » — est donc gardée à part dans **`event.homeMenu`** (alimentée à chaque « Je me sers » par `withHomeServe`) et **rétablie** quand on revient à @Home ; un ancien salon @Home qui n'en a pas encore la crée, à partir de sa carte actuelle, au premier départ. Tous les écrans qui lisent un verre (kcal de « Mes statistiques », « Qui a bu quoi », « Mes verres » de la fenêtre « Je me sers » (ouverte par « Next Drink »), historique, Drink Check) cherchent le produit dans la carte du salon **puis** dans la carte mémorisée (`findEntryForEvent`) : sans cela, les verres déjà bus perdaient leur nom (« Boisson ») et leurs kcal (« s.i. ») après un aller-retour de lieu. Les verres d'un salon dont la carte @Home avait déjà été remplacée avant cette correction ne se récupèrent pas. Le choix du lieu applique la règle de la création du salon (`settingsAfterPlacePick`) : **@Home → Mode LIBER (open bar) en euros** ; quitter @Home → retour au **Mode ORBIS** (tournées) ; tout autre changement de lieu laisse le mode et la monnaie tels quels. Le mode reste modifiable à la main ensuite, et un salon @Home dont le lieu n'est pas changé garde le mode qu'on lui a donné.
- **Devises** : `euro` ou `jeton` (avec `jetonUnitValue`).
- **Suivi calorique** : calculé sur le volume ; un bouton œil masque l'affichage mais n'est **pas mémorisé**. Dans « Mes statistiques pour ce BibaRoom » (salons classiques et @Home), un menu déroulant **« Mes verres »** (sous les cases VERRES / DÉPENSÉ / KCAL, fermé par défaut, état mémorisé par salon comme les autres menus) liste **un verre par ligne** — « - Duvel 33 cl. » (le **volume en vert fluo, sans gras**) puis, dans une colonne à droite **précédée d'une barre verticale** qui se prolonge d'une ligne à l'autre, ses kcal (« 271 kcal », ou « kcal s.i. » si le produit n'a pas de kcal connues) — dans l'ordre où ils ont été pris (`myDrinksList`, `utils.js`). Si le produit a un type de service (Bouteille, Canette, On Tap, Au verre), il est écrit sous le nom et le volume en petite pastille fine (`ServiceTag`) ; le volume reste collé à son nombre (« 44 cl. » ne se coupe jamais entre « 44 » et « cl. ») et, comme dans BibAtlas et « Qui a bu quoi », nom + volume restent sur **une seule ligne** : un nom trop long est coupé par « … », jamais le volume. Ce sont exactement les verres que compte la case VERRES (tournées, hors tournée, et « Next Drink » chez soi), donc la somme des kcal de la liste est celle de la case KCAL ; l'œil masque aussi les kcal de la liste (« — »). Au-delà de 260 px de haut la liste défile. Il n'y a pas de réglage à la création du salon. L'unité (kcal / Cal) est un réglage de profil.
- **Messagerie** : une conversation par salon (`ensure_salon_conversation`), créée dès l'ouverture du salon. Dans la liste BibaPing, un salon n'apparaît qu'une fois qu'un message (texte ou photo) y a été envoyé : le filtre porte sur le contenu du dernier message (`lastMessageBody` / `lastMessageHasMedia`) et non sur sa date, que la base renseigne déjà à la création **(base)**. Les groupes et les tête-à-tête restent listés même vides.
- **Tok** : action rapide entre participants, activable par salon (`salon_tok_settings`).
- **Clubs** : un salon peut être rattaché à un BibaClub (`biba_club_salons`) ; les membres du club sont ajoutés aux amis connus.
- **Drink Check** : l'écran `DrinkCheckScreen` (partagé avec BibaSolo) liste les produits du répertoire que l'utilisateur a consommés dans le salon — ses verres dans les tournées (ceux qui portent **son** code : dans une tournée lancée par quelqu'un d'autre, « self » désigne cette autre personne) et ses verres hors tournée ; un produit est retrouvé par `findMenuEntryById`, car un identifiant de commande est le plus souvent composé « entrée::volume » ; le lieu est pré-réglé (@Home, @Event ou le lieu lié). Il enregistre la note et publie une carte `drink_checked` **sans** créer de `drink_checkins` (le verre est déjà compté dans `round_orders`) — voir `DATABASE.md`. **Retour immédiat** : à la validation, la note donnée (ou retirée) s'affiche tout de suite (« Déjà noté ») et y reste — elle prime sur le serveur tant qu'on est sur l'écran, et la liste n'est rechargée que si les produits changent, jamais parce que l'app s'est redessinée (sinon un rechargement arrivé avant l'enregistrement de la note effaçait « Déjà noté » une dizaine de secondes) — et la popup **« Check confirmé »** (`CheckConfirmedToast`, celle du parcours depuis l'accueil, avec le nom du produit, 2,5 s) apparaît aussitôt, sans attendre la publication dans BibaPulse ; si la publication échoue, l'avertissement habituel suit. Même comportement depuis BibaSolo. **Dans le Pulse du salon** : depuis un salon (pas depuis BibaSolo), chaque check confirmé est aussi rangé dans le salon, dans `event.drinkChecks` — `{ id, code, name, drinkId, drinkName, rating, comment, photoUrl, at }`, construit par `buildDrinkCheck` / `withDrinkCheck` (`utils.js`) et enregistré par `confirmRoomDrinkCheck` (`App.jsx`) comme les autres changements du salon (`updateEvent` puis sauvegarde du bloc JSON, aucune table ni fonction SQL en plus) — et l'onglet Pulse du salon le montre à tout le monde : **« Prénom a checké Produit »** (le produit en vert fluo), puis sur la 2e ligne la **note en étoiles** (cinq étoiles de 14 px remplies au quart d'étoile, `StarsDisplay`, purement décoratives pour les lecteurs d'écran) **suivie de la note écrite « 4,5/5 »** — la note en vert fluo, « /5 » en blanc, sans décimale si la note est entière (« 4/5 ») ; rien sans note, puis le commentaire en italique sur une ligne dessous (entre guillemets, jamais interprété comme du HTML), puis la **photo** du check s'il y en a une, sur sa propre ligne sous le texte et sous l'heure, sur toute la largeur de la carte (220 px de haut au plus, comme dans BibaPulse). Sur une carte de check, l'**heure est en haut**, en face de la 1re ligne ; l'heure des tournées et des arrivées reste centrée dans la carte. **Toujours** : le check apparaît dans le Pulse du salon même si « Publier dans BibaPulse » est décoché (la visibilité Public / Mes Bibax ne concerne que la carte BibaPulse). La note est celle du check (la nouvelle note, sinon la note déjà donnée ; rien avec « Pas de note ») ; le commentaire et la photo n'existent que si la publication est cochée (les champs sont masqués sinon) ; le commentaire ne dépasse pas 280 caractères. La photo est celle déjà envoyée pour BibaPulse (`photoUrl`, bucket `pulse-photos`) : une adresse qui n'est pas du bucket BibaPulse est ignorée à l'enregistrement comme à l'affichage (`safePulsePhotoUrl`), et si la photo n'existe plus (le check a été supprimé de BibaPulse, ce qui efface aussi sa photo) l'image disparaît du Pulse du salon, le texte du check reste. Pas de plafond sur le nombre de checks gardés (comme les tournées et les verres @Home). Le badge de l'onglet Pulse compte aussi les checks, y compris les siens, comme les tournées.
- **Historique** : `EventHistoryScreen` et `EventHistoryDetailScreen` (réouverture, suppression d'une tournée ou du salon). Les totaux affichés dans ces écrans sont aujourd'hui codés à 0.

### Commandes enregistrées en base

Chaque tournée terminée est aussi enregistrée en lignes interrogeables, qui alimentent les statistiques via la vue `consumption_events` : `record_round_orders`, `mark_round_paid`, `record_partial_payment`, `record_round_tip`, `delete_round_orders`, `delete_round_tip`, `delete_round_orders_by_event`. Les scripts livrés ne prouvent que les tables `round_orders` et `round_payments` (par la vue) ; les fonctions et la table des pourboires sont **(base)**. La suppression des pourboires par événement (`deleteRoundTipsByEvent`) n'est appelée nulle part.

Un verre « Next Drink » d'un salon @Home est enregistré de la même façon : un `record_round_orders` d'**une seule ligne** (lieu `@home`, sans prix, mon code, le vrai identifiant du produit du catalogue), avec un identifiant de tournée `home-…` **propre à chaque verre** — la fonction refuse deux fois le même identifiant, et c'est ce qui permet de retirer un verre seul avec `delete_round_orders`.

Les lignes d'une **tournée** sont construites par `roundOrderRows` (`utils.js`) : un identifiant de commande est le plus souvent **composé** « entrée::volume » (`flattenMenu`), il faut donc le résoudre avec `findMenuEntryById` — jamais avec un simple `menu.find(d => d.id === …)`, qui ne trouve rien. (Avant ce correctif, les lignes de `round_orders` partaient avec `drink_id`, prix, volume et kcal à NULL, et les verres hors tournée n'étaient pas enregistrés ; les tournées déjà enregistrées ne sont pas corrigées rétroactivement.) `drink_id` est toujours le vrai identifiant du catalogue, jamais l'id local de la carte du salon ; une entrée qui ne vient pas du répertoire n'a pas de produit à compter (NULL).

Un verre pris **hors tournée** (« Ajouter une boisson hors tournée », salons classiques) est enregistré comme un verre de tournée : un `record_round_orders` d'une seule ligne (mon code, sans prix, le vrai produit, le volume choisi, les kcal), avec un identifiant `perso-<id du verre>` **propre à chaque tap** (`personalDrinkRecord`). Le « − » retire la statistique avec `delete_round_orders` (qui ne supprime que **mes** lignes) ; retirer un verre venu d'une tournée (`roundId`) ne touche pas à la statistique de la tournée. Aucune carte BibaPulse n'est publiée : c'est le rôle du Drink Check. Sans compte Bibax ou pour une boisson qui ne vient pas du répertoire, rien n'est enregistré.

## BibaMusic — playlist collaborative du salon

C'est un **écran séparé** (`BibaMusicScreen`, ouvert depuis le tableau de bord du salon), pas une section intégrée (`BibaMusicSection` est du code mort).

- **Mode MC** (identifiants internes « DJ » : `djCode`, `isDJ`) : un seul MC à la fois ; « Devenir MC » n'est proposé que s'il n'y en a pas, « Céder le rôle » pour le MC actuel.
- **Seul le MC peut supprimer** une proposition. Un non-MC ne peut **rien** supprimer, pas même sa propre proposition (le commentaire du code décrit un comportement qui n'est pas implémenté).
- **Réorganisation par glisser-déposer**, réservée au MC (appui long de 350 ms), pour les morceaux à venir ; `manualRank` prime sur le tri par Bix.
- **Bix** par morceau (cœur + compteur) ; recherche et ajout de morceaux Spotify, ou ajout manuel titre + lien.
- **Synchronisation avec Spotify** : toutes les 4 secondes, seul le morceau **en tête** de la liste à venir est replacé juste après le morceau en cours dans la playlist Spotify (ce n'est pas une synchronisation de tout le classement). Elle utilise le jeton Spotify de la personne qui a l'écran ouvert.
- **Lecture** pilotée par le MC via la fonction Edge `spotify-playback-control` ; détection du morceau joué toutes les 3 secondes. Connexion Spotify en PKCE (`ConnectScreen`).
- La carte « en cours de lecture » a le même visuel que le reste de la liste.

## Affichage — carte de salon (Home / BibaLive)

- Le bouton a `width: 100%` explicite ; le titre revient à la ligne.
- Badge « EN COURS » / « EN PAUSE » : à cheval sur le coin supérieur droit, positionnement absolu.
- Sous le titre : si le titre est personnalisé (différent du nom du lieu lié), le nom du lieu en vert fluo avec une icône de repère ; sinon la **ville**, grisée, sans code postal.
- Flèche d'accès : positionnement absolu en bas à droite.
- Le bouton « rejoindre un salon » rapide de l'accueil (`onQuickJoinSalon`) n'est pas câblé.

## Intégration BibaPulse

**Aucune carte BibaPulse n'est créée en créant, rejoignant ou en utilisant un BibaRoom** : le `venue_visit` ne vient que du check-in depuis la **fiche d'un lieu**. Depuis un salon, seul le Drink Check publie une carte `drink_checked` (avec le lieu du salon comme `venue_id`). Le même check est aussi rangé dans le salon lui-même (`event.drinkChecks`) pour son onglet Pulse, publié ou non dans BibaPulse. `room_salon_code` n'est jamais renseigné. Voir `BIBAPULSE.md`.
