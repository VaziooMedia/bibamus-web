# BIBAMUS — Contexte du projet

> Ce document est la référence générale de Bibamus. Il doit permettre à une nouvelle conversation Claude — ou à toute personne rejoignant le projet — de comprendre rapidement ce qu'est Bibamus sans relire l'historique des échanges. Il reste volontairement une synthèse : le détail de chaque module est dans les documents spécialisés listés en fin de fichier.
> Dernière mise à jour : 2026-10-24 (liens @nom, recherche par @nom, aperçus de partage ; 2026-10-09 pour le reste). Les faits du produit et de la pile technique sont vérifiés contre le code de l'app (`src/`, version `26.32`). Les passages d'intention (vision, public visé) ne sont pas vérifiables dans le code et sont repris tels quels. Ce qui relève d'un autre dépôt ou d'un service externe est marqué **(hors dépôt)**.

---

## Vision générale

**Bibamus est l'application sociale qui connecte les gens autour des boissons, des lieux et des moments partagés, portée par une base de données complète dédiée à l'univers des boissons.**

- **Public visé** : grand public consommateur dans un premier temps ; élargissement aux professionnels (établissements, marques, producteurs) une fois l'audience suffisamment étendue. Le code prépare déjà ce passage : parcours de revendication d'une fiche (`ClaimModal`, drapeau `claims_enabled`), trois niveaux de certification (utilisateur, Bibamus, producteur).
- **Logique sociale** : les activités réalisées dans Bibamus (déguster, checker, rejoindre un salon, contribuer à la base de données) génèrent naturellement le contenu social de l'app — jamais un réseau social généraliste où l'on publie n'importe quoi. Le code le confirme : aucun écran de rédaction libre dans BibaPulse ; les cartes viennent des checks.
- **Identité propre** : le vocabulaire et les mécaniques sont pensés pour ne pas être une copie d'Instagram ou de Snapchat avec un vernis « boissons ». Le **Bix** (équivalent du « like ») en est l'exemple le plus concret. Signature : **Connect. Drink. Bix.** (intention produit : cette phrase n'apparaît nulle part dans le code).

## Architecture fonctionnelle — vue d'ensemble

| Module | Rôle |
|---|---|
| **Home** | Accueil : Stories, BibaLive (salons en cours, section de l'accueil et non un écran), aperçu BibaPulse (3 dernières cartes), suggestions Bibax (3 affichées), six tuiles — BibaGo, BibaPlay, BibaMeet *(« Soon »)*, BibAtlas, BibaCal *(« Soon »)*, BibaPing — et quatre boutons ronds (recherche, BibaSolo, DrinkCheck, PlaceCheck). BibaPulse n'a pas de tuile : il est dans la barre basse |
| **BibaGo** | Trois cartes : **BibaRoom** (créer / rejoindre), **BibaSolo** et BibArena *(« Soon »)* |
| **BibaRoom** | Salon partagé (tournées, cagnotte, addition, consommation libre) à trois onglets Room / Pulse / Ping — voir `BIBAROOM.md` |
| **BibaSolo** | Journal personnel de consommations sans salon : boisson, prix en € ou en jetons, lieu optionnel, calories, BibaZERO et WaterAlert solo |
| **BibaMusic** | Playlist collaborative d'un BibaRoom (Spotify, Bix par morceau) |
| **BibArena** | Événements de plus grande envergure — **non construit** : carte « Soon », aucun écran |
| **BibaPulse** | Fil d'activité social — voir `BIBAPULSE.md` |
| **BibAtlas** | Répertoire : lieux, produits, marques, producteurs ; recherche, carte, lecture d'étiquette par IA, revendication de fiche |
| **Bibax** | Le compte utilisateur et la relation **mutuelle** entre deux comptes (demande + confirmation) — voir `BIBAX.md`. Dans le code, l'ancien nom « Bibro » subsiste (`BibrosScreens`, `myBibroCode`) |
| **Stories** | Contenu éphémère de 24 h ; contextes `global`, `room` et `official` — voir `STORIES.md` |
| **BibaPing** | Messagerie : tête-à-tête, groupes, chat de salon |
| **BibaPlay** | Plateforme de jeux avec un seul jeu, **Predict** (pronostics sportifs entre amis) ; carte « D'autres jeux : Bientôt » |
| **BibaMe** | Hub profil : Mes BibaClub, Mes Statistiques (dont **Wrapped**, « Ton année Bibamus »), Mes Produits, Mes Favoris, Mon Historique, Mes Photos, BibaCare *(« Bientôt »)*, réglages — voir `PROFILE.md` |
| **BibaClub** | Clubs ; un salon peut être rattaché à un club |
| **BibaZERO / WaterAlert / BibAzard** | BibaZERO : statut par participant pour qui ne boit pas, avec PIN et joker, **hors modes de salon** et aussi en BibaSolo ; WaterAlert : rappels d'eau ; BibAzard : roulette de boisson au hasard |
| **DrinkCheck / PlaceCheck** | Accès rapides de l'accueil vers le répertoire de produits ou de lieux avec un flux de check |
| **Transverses** | Notifications, recherche globale, paramètres (compte, sécurité, notifications, préférences, apparence, connexions, aide), import de données (administrateurs) |

Non construits à ce jour (cartes ou tuiles « Soon » ou « Bientôt ») : BibArena, BibaMeet, BibaCal, BibaCare, autres jeux de BibaPlay, thème personnalisable, vidéo dans les Stories, export image de Wrapped, lecture des codes-barres (drapeau `BARCODE_SCAN_ENABLED = false` : la caméra sert à lire l'étiquette).

**Vocabulaire à noter** : « BibaCheck » n'existe pas dans le code (il dit DrinkCheck et PlaceCheck) ; « BibaZERO » s'écrit parfois `BibaZero` ; l'ancien nom « BibaBob » subsiste dans les identifiants de code.

## Pile technique

- **Frontend app** : React 18 et Vite 5, JavaScript / JSX (pas de TypeScript), dépôt GitHub `VaziooMedia/bibamus-web` (**public**). Déployé sur Vercel *(hors dépôt : seuls indices, `vercel.json` — réécriture SPA et règle réservée aux robots pour les liens `/@nom` — et le dossier `api/`)*, domaine `bibamus.app`, qui redirige vers `www.bibamus.app` (adresse définitive, constaté le 2026-10-25 ; les aperçus de partage et l'adresse officielle des pages publiques utilisent `www`, les liens partagés par l'app passent par la redirection) *(hébergeur du domaine hors dépôt)*.
- **Plateforme de gestion** : dépôt GitHub distinct `VaziooMedia/Bibamus-Management`, annoncée sur `admin.bibamus.app` **(hors dépôt)** — voir `ADMIN-PLATFORM.md`.
- **Backend** : Supabase, projet `rkmmrzkqzqpntgiguajz` (celui du client de l'app). Le partage du même projet avec la plateforme de gestion est très probable mais **non prouvé** depuis ce dépôt.
- **Fonctions Edge** appelées par l'app : `read-label`, `moderate-and-upload-photo`, `create-pulse-event`, `delete-pulse-post`, `delete-pulse-check`, `upload-pulse-photo`, `delete-my-account`, `send-push-notification`, `Spotify-playback-control-ts`, `geoapify-geocode`, `google-place-hours`. `ai-complete-entity` est utilisée par la plateforme de gestion seulement. Elles se déploient séparément de l'app. Les sources livrées avec les scripts SQL (hors dépôt) sont : create-pulse-event (v3, v4, v5, v6, v7), delete-pulse-post, delete-pulse-check, read-label, send-push-notification, spotify-playback-control, upload-pulse-photo, ai-complete-entity.
- **Services tiers** : Firebase Cloud Messaging (notifications push), Spotify (API, connexion PKCE), Geoapify (autocomplétion d'adresse), Google Places (horaires, via fonction Edge), BigDataCloud (géocodage inverse du pays), Leaflet et tuiles OpenStreetMap (cartes), Google Cloud Vision (modération de photos), OpenAI (lecture d'étiquette, propositions de la plateforme de gestion), `@zxing` (bibliothèque de lecture de codes-barres). Voir `GEOLOCATION.md`.
- **Workflow de déploiement** : le dépôt montre un flux Git par branche (branche de travail, poussée sur `origin`, fusion dans `main` puis redéploiement). Historiquement : édition locale, zip, dépôt sur GitHub. Les changements SQL sont livrés en scripts `.sql` à exécuter à la main dans l'éditeur SQL de Supabase ; la plupart des objets de base (tables `salons`, `stories`…, nombreuses fonctions) ne sont **pas** dans le dépôt — voir `DATABASE.md`.
- **Drapeaux de fonctionnalités** : table `feature_flags` (+ surcharges par pays), valeur « visible » si la clé est absente. Utilisés par le code : `signups_enabled`, `maintenance_mode`, `nav_bibameet_visible`, `nav_bibapulse_visible`, `nav_games_visible`, `nav_bibaping_visible`, `nav_atlas_visible`, `stories_enabled`, `claims_enabled`.
- **i18n** : l'app est **monolingue** (français) ; aucune bibliothèque d'internationalisation. Seules existent des structures préparatoires (styles `{ code, fr }`, colonnes `translations` des fiches). La cible EN / NL / DE n'est pas commencée — voir `MULTILINGUAL.md`.
- **Version** : `APP_VERSION` dans `constants.js`, à incrémenter à chaque envoi.

## Décisions validées

- **Le Bix remplace le « like » partout** dans l'interface (aucun « J'aime » affiché). Quelques résidus techniques subsistent dans le code (`PRODUCT_LIKED`, `toggleVenueLike`). Le Bix est une trace de qui a réagi dans BibaPulse ; dans les Stories et BibaMusic, l'interface n'affiche aujourd'hui qu'un compteur.
- **BibaPulse** : le contenu est généré par les actions réelles dans l'app et par les publications libres (bouton « + », avec photo, tags de fiche, Bibax tagués et partage en Story possible). Le client n'offre que deux visibilités, « Public » et « Mes Bibax » (`relations`) ; le défaut est `public` pour un Drink Check, `relations` pour un Place Check. Le regroupement (anti-doublon sur 30 minutes) se fait côté serveur.
- **Bibax mutuel** (demande + confirmation) plutôt qu'un suivi à sens unique. La visibilité « relations » repose sur les Bibax confirmés. Le suivi à sens unique entre personnes n'est plus utilisé (`toggleFollow` n'a plus d'appelant) ; en revanche le **suivi de lieux et de produits est actif** (cloche sur les fiches) et une cloche « Suivre sur Pulse » existe sur la fiche d'un Bibax.
- **Stories V1** : le contexte (où c'est créé : `global`, `room`, `official`) est séparé de l'audience (qui la voit). Une Story de salon peut être partagée dans BibaPulse sans duplication. `arena` n'existe que comme réglage de préférences : aucun code ne crée de Story `arena`.
- **BibaRoom** : le code du salon (6 caractères) fait office de clé d'accès ; les Stories de salon suivent le même principe.
- **Localisation des profils** : « Commune de résidence » obligatoire à l'enregistrement du profil (à l'inscription, seul le pays est demandé) ; elle est **suggérée par pays mais en texte libre** côté client (liste de 6 suggestions au plus, pas de liste fermée). « Ville / Village » optionnel en texte libre (aucun écran ne l'édite aujourd'hui). « Région » abandonnée.
- **Nom d'utilisateur (@nom)** (distinct du prénom, du nom et du surnom) — décision du 2026-10-23, qui **remplace** l'abandon précédent (dont la justification, « l'ajout d'un Bibax se fait par code, jamais par recherche », était périmée : on ajoute aussi un Bibax par QR code et par recherche de nom, le nom affiché respectant les réglages de partage). Chaque compte, lieu, marque et producteur a un nom d'utilisateur unique, dans un **espace de noms commun** (la casse est ignorée : deux noms qui ne diffèrent que par la casse sont le même). Au départ, c'est une **copie du code** : le code Bibax pour un compte, un code aléatoire de même forme pour un lieu, une marque ou un producteur ; le code lui-même ne change jamais et reste réservé à son propriétaire. Un compte peut changer le sien **une seule fois** (Compte → Nom d'utilisateur). Les administrateurs le modifient sans limite depuis la plateforme de gestion (section « Nom d'utilisateur » de la fiche d'un compte, d'un lieu, d'une marque ou d'un producteur, depuis le 2026-10-24) ; les gérants de fiches pourront le faire depuis la plateforme Business, qui n'est pas encore construite. Règles : 6 à 30 caractères ; lettres (majuscules et minuscules), chiffres, point, tiret bas et tiret ; début et fin par une lettre ou un chiffre ; une liste de mots réservés est refusée, ainsi que tout nom contenant « bibamus ». **Recherche par @nom exact** (depuis le 2026-10-24) : « Ajouter un Bibax » accepte un @nom (champ « Rechercher un Bibax ou un @nom »), et la recherche de l'accueil, pour une saisie qui commence par « @ », retrouve un compte, un lieu, une marque ou un producteur ; la casse est ignorée, il n'y a pas de recherche partielle et pas de nouveau réglage de confidentialité (mêmes informations visibles et mêmes blocages que pour le code ; un compte désactivé est introuvable). **Liens partageables `bibamus.app/@nom`** (depuis le 2026-10-24, dans l'app seulement) : « Compte → Nom d'utilisateur » montre « Ton lien » (à copier ou à partager) ; les fiches lieu, marque et producteur ont un bouton « Partager » qui partage ce lien (le lien général `bibamus.app` si la fiche n'a pas encore de @nom) ; les boissons n'ont pas de @nom et gardent le lien général ; le profil d'un autre Bibax n'a pas de bouton de partage. Ouvert par une personne connectée, le lien ouvre directement le compte (aperçu du profil), le lieu, la marque ou le producteur ; sans compte connecté, il est gardé sur l'appareil (24 h au plus, un seul à la fois) et ouvert juste après la connexion ou l'inscription. Un lien qui ne mène à rien (nom inconnu, compte bloqué ou désactivé, fiche non publiée) affiche toujours le même message neutre. **Fiches fusionnées — décision et mise en ligne du 2026-10-25** : quand une fiche est absorbée par une autre (statut « doublon »), son ancien lien continue de marcher et ouvre la fiche conservée — dans l'app, dans la recherche par @nom et pour les visiteurs sans compte (carte publique et aperçus de partage, avec le @nom de la fiche conservée) ; la redirection suit la chaîne si la fiche conservée est elle-même absorbée plus tard. L'ancien @nom est **libéré** (choix de Mehdi) : une autre fiche ou un compte peut le reprendre, et son nouveau porteur l'emporte alors toujours sur la redirection, même si sa page n'est pas visible (un compte, un brouillon, un compte qui a bloqué la personne). Pas de redirection non plus quand deux fiches absorbées ont porté le même nom (on ne devine pas) ni quand la fiche conservée n'est pas visible : le message neutre s'affiche. Rien à changer dans l'app pour cela (voir `DATABASE.md`). **Pages publiques — décisions du 2026-10-24** : une personne sans compte qui ouvre le lien d'un lieu, d'une marque ou d'un producteur verra une **carte résumé** (nom, photo, type, ville, pays, et un bouton « Ouvrir dans Bibamus » ; ni adresse, ni horaires, ni contact, ni produits) ; **seules les fiches « complet »** ont une carte ; cette carte est **indexable par Google** (pas de plan de site pour l'instant) ; **un compte n'a jamais de page publique** : le lien d'un compte et un nom inconnu donnent exactement la même réponse (écran de connexion, aperçu générique non indexé). **Livré** : la fonction de base `get_public_card` (en production depuis le 2026-10-24, voir `DATABASE.md`) ; les **aperçus de partage** (titre, description et image du lien dans WhatsApp, Messenger, Google, Telegram..., en production et constatés le 2026-10-25), produits par une fonction Vercel `api/at.js` que `vercel.json` réserve aux robots — une personne qui ouvre le lien reçoit l'app comme avant ; un compte, un nom inconnu ou une fiche pas encore « complet » donnent un aperçu général, identique et non indexé ; et, avec cette mise à jour, **la carte publique dans l'app** : une personne sans compte qui ouvre le lien d'une fiche « complet » voit d'abord la carte (nom, photo de profil et de couverture, genre — Lieu, Marque ou Producteur —, jusqu'à trois types, ville et pays, et le bouton « Ouvrir dans Bibamus »), puis l'écran de connexion ou d'inscription ; le lien reste mémorisé (24 h au plus) et ouvre la fiche complète juste après la connexion. Un compte, un nom inconnu, une fiche pas encore « complet » ou une base qui ne répond pas (délai de 6 secondes) mènent directement à l'écran de connexion, sans carte ni message, et de la même façon. Une personne sans compte qui revient sur le site dans les 24 h après avoir ouvert un lien revoit cette carte. **Pas encore construit** : changement du @nom par les gérants (plateforme Business), plan de site pour Google.
- **Horaires d'établissements** : toujours issus de Google, jamais encodés à la main dans l'app.
- **Fiche produit à trois onglets** : « Infos », « Biba360 » (au milieu ; le « 360 » en vert fluo) et « BibaPulse ». Biba360 réunit les statistiques du produit : tout en haut la carte « Notes » (la note étoilée en trois lignes : la tienne, la moyenne de tes Bibax, et la moyenne Bibamus, la même que sur la bannière), puis un seul bloc en trois sections séparées par une barre verte fluo : « Checks » (tes checks, ceux de tes Bibax, le total de tous les utilisateurs), « Unique Checkers » (le nombre de **personnes différentes** qui ont checké le produit : tes Bibax, tous les utilisateurs), puis la courbe « Check Trends » (la popularité du produit au fil du temps, tous les verres de tous les utilisateurs, en chiffres anonymes : 7 jours, 30 jours, 12 mois ou tout l'historique ; affichée seulement si au moins 2 personnes différentes ont consommé le produit), ton « historique avec ce produit » (première et dernière fois, nombre de consommations, tes lieux les plus fréquents — tous tes verres, visible par toi seul) la liste nommée de tes Bibax (du plus au moins de checks, sans limite) et, en dernier, « Où ce produit est le plus consommé ? » (le classement des lieux — 5 au plus, chacun avec un bouton rond « > » vers sa fiche — en deux sous-onglets « Tout le monde », en chiffres anonymes, et « Mes Bibax ») ; il est appelé à s'enrichir. La liste des Bibax ne montre que les Bibax confirmés qui partagent leurs statistiques « Boissons » : **aucun réglage de partage supplémentaire** (voir `DATABASE.md`, `PROFILE.md`) ; le classement « Mes Bibax » exige en plus que le Bibax partage « Lieux ». Le même bouton rond « > » est posé, juste à côté du nom (et non en bout de ligne après le chiffre ; petit cercle de 14 px, posé sur la première ligne du nom quand celui-ci passe sur deux lignes), sur les lieux de « Où tu l'as bu », ceux du classement et sur les Bibax de la liste (profil ; la liste ne montre que les 5 premiers, puis un bouton « Voir tout » ouvre une page avec la liste complète) ; en revenant de la fiche du lieu, du profil ou de la page « Voir tout », on retombe sur Biba360, au même niveau que l'élément cliqué (voir `DATABASE.md`).
- **Pastilles de style cliquables (fiche produit, onglet Infos)** — décision du 2026-10-25 : toucher une pastille de style la **sélectionne** (fond vert ; la retoucher la retire). Dès qu'au moins un style est choisi, un bloc « N style(s) choisi(s) » avec le bouton **« Produits communs »** apparaît sous la carte d'infos (rien n'apparaît tant qu'aucun style n'est choisi). Ce bouton ouvre la liste « Produits » dans la **catégorie du produit**, limitée aux produits qui portent **tous** les styles choisis (ET) : une puce par style (« Filtré : <style> ✕ », puis « <style> ✕ »), dont le ✕ retire ce style — le dernier retiré lève le filtre. Choix de Mehdi après comparaison de trois maquettes (sélection depuis la fiche, plutôt que suggestions dans la liste ou bouton « + Style »). Le filtre transmet les codes séparés par des virgules (`value: "ipa,american_ipa"`) ; la sélection n'est pas conservée quand on revient à la fiche. La flèche retour de cette liste ramène à la fiche d'origine et remet la liste des produits comme on l'avait laissée — même après avoir retiré toutes les puces (la liste des catégories n'est jamais visitée : seul un niveau « lettre » éventuel se remonte d'abord) ; une fiche ouverte depuis la liste filtrée peut elle-même lancer une autre liste filtrée, chaque retour revient d'un cran (pile `drinkTagTrips` dans `App.jsx`). Quand un filtre est actif, la liste n'est plus regroupée par lettre (les comptages par lettre portent sur toute la catégorie). Seules les pastilles de style sont cliquables pour l'instant (les icônes Bio, Sans gluten, pays… de la liste Produits l'étaient déjà). La liste Produits affiche le **nombre total de résultats** (« 23 produits ») au-dessus des lignes — pour une recherche, un filtre ou une lettre — et la flèche flottante « Remonter en haut » y est de nouveau visible (elle ne s'affichait plus nulle part : voir `DESIGN-SYSTEM.md`).
- **Ligne des caractéristiques (fiche produit, onglet Infos)** — décision du 2026-10-29 : sous la ligne « ABV / IBU / EBC » de la carte d'infos, une ligne montre les caractéristiques du produit, **dans cet ordre : palier d'alcool, Bio, Sans gluten** (`getDrinkFeatureItems`, `DrinkDisplay.jsx`). Chaque critère est une petite pastille — la même que dans les listes de l'app (le palier d'alcool en texte, Bio et Sans gluten en icônes) —, séparée de la suivante par un **point vert fluo de 4 px**, comme sur la ligne ABV / IBU / EBC ; la ligne est séparée de celles du dessus et du dessous par un **trait gris fin**. Les règles d'affichage sont celles de l'app : le palier d'alcool suit la règle des trois paliers ci-dessous (jamais pour les softs, boissons chaudes et snacks), Bio et Sans gluten pour les bières et cidres seulement. Un produit sans aucun de ces critères n'a ni ligne ni trait en plus ; les pastilles ne sont pas cliquables. Choix de Mehdi après comparaison de deux maquettes (pastilles, ou icônes seules). **Pas encore affichés, volontairement** : les autres caractéristiques prévues côté Gestion, faute d'icône pour l'instant (à ajouter plus tard, dans `DRINK_FEATURE_KEYS`) ; le badge « Générique », le badge « Alc. » et le drapeau du pays ne font pas partie de cette ligne.
- **Label ATP — Authentic Trappist Product (fiche produit, onglet Infos)** — décision du 2026-10-30 : les bières trappistes certifiées portent le label ATP, montré par **une grande icône de 56 px de haut** (`src/assets/brand/atp.svg`, hexagone vert fluo « Authentic Trappist Product ») **sur la ligne de l'origine** (ville, région, pays), **à son extrême droite** et centrée en hauteur par rapport à ces lignes ; le texte d'origine reste à gauche (au moins 12 px d'écart). Elle n'a donc plus de ligne à elle (première version du même jour : ligne séparée sous les caractéristiques, abandonnée car une ligne entière pour une seule icône était dommage) ; la ligne d'origine prend la hauteur de l'icône (56 px) quand le texte est plus court. Un produit **sans aucune origine** a quand même cette ligne, avec l'icône seule à droite ; un produit qui n'a que l'ATP comme information affiche la carte d'infos avec l'icône seule. L'icône n'est pas cliquable. L'information vient de la gestion : c'est une **caractéristique du produit** (liste « Caractéristiques & labels », créée le 2026-10-30 sous le nom « Authentic Trappist Product (ATP) », code `perso_authentic_trappist_product_atp`, constante `ATP_CHARACTERISTIC_CODE` dans `utils.js`). L'app lit désormais la liste `characteristics` de chaque produit (`rowToDrink`, `sharedDirectories.js`) mais n'en utilise que ce code, et ne l'écrit jamais. Sans ATP, rien ne change. **Attention** : renommer le label dans la gestion ne change pas le code (l'icône reste) ; le supprimer dans la gestion le retire de tous les produits, donc l'icône disparaît partout. Pas de filtre « ATP » dans l'Annuaire pour l'instant.
- **Paliers d'alcool (pastilles)** — décision du 2026-10-30 : en Belgique une bière à 0,1–0,5 % est « sans alcool » mais n'est pas à 0,0 %, donc « 0.0% » seul était trompeur. Trois paliers, définis une seule fois dans `getAlcoholTierBadge` (`utils.js`) et utilisés partout où une pastille d'alcool s'affiche (`DrinkDisplay.jsx` : listes et fiche produit ; produits d'une catégorie de salle ; BibaSolo) : **« 0.0% »** si le degré vaut exactement 0 ; **« Alcohol free »** de 0,1 à 0,5 % inclus ; **« Alcohol low »** de 0,6 à 3,0 % inclus ; au-delà de 3,0 % ou degré inconnu, aucune pastille. Ces deux derniers libellés sont du texte, faute d'icône lisible (l'icône « Low ABV » essayée a été écartée : son texte n'est pas lisible à 16 px ; son fichier a été retiré du dépôt). Le seuil légal de `isAlcoholicDrink` (> 0,5 % = alcoolisé : BibaZERO, statistiques) ne change pas. Dans l'Annuaire, chaque pastille cliquable filtre sur son palier (`zero`, `alcoholFree`, `alcoholLow`) ; le filtre est calculé côté base par `get_drinks_page`, qui doit connaître ces trois valeurs.
- **Onglets harmonisés (fiches Produits/Lieux, BibaClub, BibaRoom)** — décision du 2026-10-30 : un seul aspect, celui des fiches Produits et Lieux (composant `PillTabs`) : pastilles rondes, onglet actif plein vert fluo, **sans icônes**, avec un filet de séparation au-dessus et en dessous de la rangée. Un **BibaClub** a désormais trois onglets « BibaPulse » (ancien « Fil »), « Biba360 » (ancien « Stats ») et « Bibax » (ancien « Membres », le « x » en vert fluo), dans cet ordre ; seuls les libellés et l'ordre changent. Un **BibaRoom** garde « BibaRoom », « BibaPulse » et « BibaPing » avec leurs pastilles rouges de non lus, mais perd ses icônes.

## Décisions abandonnées

- Suivi « follows » à sens unique pour la visibilité BibaPulse — remplacé par le système Bibax mutuel.
- **BibaFree** (salon solo) — retiré. Le besoin « solo » est servi par un module distinct, **BibaSolo**, et non par un BibaRoom à une seule personne (un paramètre `mode` « solo » reste par défaut dans `NewEventScreen`, sans écran qui l'utilise).
- Ancien nom d'utilisateur libre (colonne `profiles.username`, renseignée pour trois comptes seulement, jamais utilisée comme identifiant de recherche) — remplacé le 2026-10-23 par le nom d'utilisateur @nom (voir Décisions validées).
