## Vision générale

**Bibamus est l'application sociale qui connecte les gens autour des boissons, des lieux et des moments partagés, portée par une base de données complète dédiée à l'univers des boissons.**

- **Public visé** : grand public consommateur dans un premier temps ; élargissement aux professionnels (établissements, marques, producteurs) une fois l'audience suffisamment étendue. Le code prépare déjà ce passage : parcours de revendication d'une fiche (`ClaimModal`, drapeau `claims_enabled`), trois niveaux de certification (utilisateur, Bibamus, producteur).
- **Logique sociale** : les activités réalisées dans Bibamus (déguster, checker, rejoindre un salon, contribuer à la base de données) génèrent naturellement le contenu social de l'app — jamais un réseau social généraliste où l'on publie n'importe quoi. Le code le confirme : aucun écran de rédaction libre dans BibaPulse ; les cartes viennent des checks.
- **Identité propre** : le vocabulaire et les mécaniques sont pensés pour ne pas être une copie d'Instagram ou de Snapchat avec un vernis « boissons ». Le **Bix** (équivalent du « like ») en est l'exemple le plus concret. Signature : **Connect. Drink. Bix.** (intention produit : cette phrase n'apparaît nulle part dans le code).

| **BibAtlas** | Répertoire : lieux, produits, marques, producteurs ; recherche, carte, lecture d'étiquette par IA, revendication de fiche |
| **Bibax** | Le compte utilisateur et la relation **mutuelle** entre deux comptes (demande + confirmation) — voir `BIBAX.md`. Dans le code, l'ancien nom « Bibro » subsiste (`BibrosScreens`, `myBibroCode`) |
| **Stories** | Contenu éphémère de 24 h ; contextes `global`, `room` et `official` — voir `STORIES.md` |

## Pile technique

- **Frontend app** : React 18 et Vite 5, JavaScript / JSX (pas de TypeScript), dépôt GitHub `VaziooMedia/bibamus-web` (**public**). Déployé sur Vercel *(hors dépôt : seuls indices, `vercel.json` — réécriture SPA et règle réservée aux robots pour les liens `/@nom` — et le dossier `api/`)*, domaine `bibamus.app`, qui redirige vers `www.bibamus.app` (adresse définitive, constaté le 2026-10-25 ; les aperçus de partage et l'adresse officielle des pages publiques utilisent `www`, les liens partagés par l'app passent par la redirection) *(hébergeur du domaine hors dépôt)*.
- **Plateforme de gestion** : dépôt GitHub distinct `VaziooMedia/Bibamus-Management`, annoncée sur `admin.bibamus.app` **(hors dépôt)** — voir `ADMIN-PLATFORM.md`.
- **Backend** : Supabase, projet `rkmmrzkqzqpntgiguajz` (celui du client de l'app). Le partage du même projet avec la plateforme de gestion est très probable mais **non prouvé** depuis ce dépôt.
- **Fonctions Edge** appelées par l'app : `read-label`, `moderate-and-upload-photo`, `create-pulse-event`, `delete-pulse-post`, `delete-pulse-check`, `upload-pulse-photo`, `delete-my-account`, `send-push-notification`, `Spotify-playback-control-ts`, `geoapify-geocode`, `google-place-hours`. `ai-complete-entity` est utilisée par la plateforme de gestion seulement. Elles se déploient séparément de l'app. Les sources livrées avec les scripts SQL (hors dépôt) sont : create-pulse-event (v3, v4, v5, v6, v7), delete-pulse-post, delete-pulse-check, read-label, send-push-notification, spotify-playback-control, upload-pulse-photo, ai-complete-entity.
- **Services tiers** : Firebase Cloud Messaging (notifications push), Spotify (API, connexion PKCE), Geoapify (autocomplétion d'adresse), Google Places (horaires, via fonction Edge), BigDataCloud (géocodage inverse du pays), Leaflet et tuiles OpenStreetMap (cartes), Google Cloud Vision (modération de photos), OpenAI (lecture d'étiquette, propositions de la plateforme de gestion), `@zxing` (bibliothèque de lecture de codes-barres). Voir `GEOLOCATION.md`.
- **Workflow de déploiement** : le dépôt montre un flux Git par branche (branche de travail, poussée sur `origin`, fusion dans `main` puis redéploiement). Historiquement : édition locale, zip, dépôt sur GitHub. Les changements SQL sont livrés en scripts `.sql` à exécuter à la main dans l'éditeur SQL de Supabase ; la plupart des objets de base (tables `salons`, `stories`…, nombreuses fonctions) ne sont **pas** dans le dépôt — voir `DATABASE.md`.
- **Drapeaux de fonctionnalités** : table `feature_flags` (+ surcharges par pays), valeur « visible » si la clé est absente. Utilisés par le code : `signups_enabled`, `maintenance_mode`, `nav_bibameet_visible`, `nav_bibapulse_visible`, `nav_games_visible`, `nav_bibaping_visible`, `nav_atlas_visible`, `stories_enabled`, `claims_enabled`.
- **i18n** : l'app est **monolingue** (français) ; aucune bibliothèque d'internationalisation. Seules existent des structures préparatoires (styles `{ code, fr }`, colonnes `translations` des fiches). La cible EN / NL / DE n'est pas commencée — voir `MULTILINGUAL.md`.
- **Version** : `APP_VERSION` dans `constants.js`, à incrémenter à chaque envoi.

## Décisions validées

- **Le Bix remplace le « like » partout** dans l'interface (aucun « J'aime » affiché). Quelques résidus techniques subsistent dans le code (`PRODUCT_LIKED`, `toggleVenueLike`). Le Bix est une trace de qui a réagi dans BibaPulse ; dans les Stories et BibaMusic, l'interface n'affiche aujourd'hui qu'un compteur.
- **BibaPulse** : le contenu est généré par les actions réelles dans l'app et par les publications libres (bouton « + », avec photo, tags de fiche, Bibax tagués et partage en Story possible). Le client n'offre que deux visibilités, « Public » et « Mes Bibax » (`relations`) ; le défaut est `public` pour un Drink Check, `relations` pour un Place Check. Le regroupement (anti-doublon sur 30 minutes) se fait côté serveur.
- **Bibax mutuel** (demande + confirmation) plutôt qu'un suivi à sens unique. La visibilité « relations » repose sur les Bibax confirmés. Le suivi à sens unique entre personnes n'est plus utilisé (`toggleFollow` n'a plus d'appelant) ; en revanche le **suivi de lieux et de produits est actif** (cloche sur les fiches) et une cloche « Suivre sur Pulse » existe sur la fiche d'un Bibax.
- **Stories V1** : le contexte (où c'est créé : `global`, `room`, `official`) est séparé de l'audience (qui la voit). Une Story de salon peut être partagée dans BibaPulse sans duplication. `arena` n'existe que comme réglage de préférences : aucun code ne crée de Story `arena`.
- **BibaRoom** : le code du salon (6 caractères) fait office de clé d'accès ; les Stories de salon suivent le même principe.
- **Localisation des profils** : « Commune de résidence » obligatoire à l'enregistrement du profil (à l'inscription, seul le pays est demandé) ; elle est **suggérée par pays mais en texte libre** côté client (liste de 6 suggestions au plus, pas de liste fermée). « Ville / Village » optionnel en texte libre (aucun écran ne l'édite aujourd'hui). « Région » abandonnée.
- **Inscription en 3 étapes, tutoyée (décidé le 2026-11-08, `AuthScreen.jsx`, puis `HomeTour.jsx`)** — le long formulaire de 8 champs est remplacé par **trois écrans d'une question légère chacun**, avec une barre de progression (3 segments vert fluo + « Étape 1 sur 3 ») et **un titre seul, sans phrase explicative dessous** (retirées à la demande de Mehdi) : **1. « Enchanté ! »** prénom, nom, surnom (optionnel) et la note sur ce que les autres Bibax pourront voir (prénom, nom et surnom : le nom d'utilisateur n'est pas choisi à l'inscription, il n'y est donc pas cité) ; **2. « Encore deux infos »** date de naissance et pays (pré-rempli par la position de l'appareil, comme avant) ; **3. « Dernière étape »** email, mot de passe et sa confirmation, bouton « Créer mon compte ». Chaque étape est contrôlée avant de passer à la suivante, avec des messages courts (« Il manque ton prénom. », « Choisis ton pays. »…) ; **l'âge minimum du pays (`market_config`) est vérifié dès l'étape 2**, donc quelqu'un qui n'a pas l'âge n'a pas à remplir la suite, puis revérifié à l'envoi (c'est cette vérification qui fait foi). « Retour » ramène à l'étape d'avant en gardant tout ce qui a été saisi. Les champs obligatoires, les données envoyées à `signUp` et la base sont **inchangés** (aucun SQL). **Ton : tutoiement partout dans l'inscription, la connexion, le mot de passe oublié et l'écran de confirmation** (« Inscris-toi », « Connecte-toi », « Vérifie ta boîte mail ») ; « sympa et discret » : quelques mots chaleureux et un émoji, pas d'humour appuyé ; les textes sur la vie privée et l'âge gardent leur sens d'origine, seulement tutoyés. Le conteneur de l'écran compte maintenant son remplissage dans les 100 % de hauteur : une étape tient dans l'écran sans défiler (avant, l'écran de connexion défilait de 64 px pour rien). **Animations (étape C, 2026-11-08, « sympa et discret »)** : le logo de l'écran est désormais un SVG intégré (`BibamusLogo.jsx`, mêmes tracés que `public/bibamus-logo.svg`, pixel pour pixel) dont les **trois éclats au-dessus de la bouteille** jaillissent à l'affichage puis scintillent de temps en temps ; une étape **glisse doucement en place** (de la droite en avançant, de la gauche avec « Retour », 0,3 s) avec son titre ; la **barre de progression se remplit** (0,45 s) ; un **message d'erreur tressaute** une fois ; un bouton **s'enfonce un peu** quand on appuie. - **Nom d'utilisateur (@nom)** (distinct du prénom, du nom et du surnom) — décision du 2026-10-23, qui **remplace** l'abandon précédent (dont la justification, « l'ajout d'un Bibax se fait par code, jamais par recherche », était périmée : on ajoute aussi un Bibax par QR code et par recherche de nom, le nom affiché respectant les réglages de partage). Chaque compte, lieu, marque et producteur a un nom d'utilisateur unique, dans un **espace de noms commun** (la casse est ignorée : deux noms qui ne diffèrent que par la casse sont le même). Au départ, c'est une **copie du code** : le code Bibax pour un compte, un code aléatoire de même forme pour un lieu, une marque ou un producteur ; le code lui-même ne change jamais et reste réservé à son propriétaire. Un compte peut changer le sien **une seule fois** (Compte → Nom d'utilisateur). Les administrateurs le modifient sans limite depuis la plateforme de gestion (section « Nom d'utilisateur » de la fiche d'un compte, d'un lieu, d'une marque ou d'un producteur, depuis le 2026-10-24) ; les gérants de fiches pourront le faire depuis la plateforme Business, qui n'est pas encore construite. Règles : 6 à 30 caractères ; lettres (majuscules et minuscules), chiffres, point, tiret bas et tiret ; début et fin par une lettre ou un chiffre ; une liste de mots réservés est refusée, ainsi que tout nom contenant « bibamus ». **Recherche par @nom exact** (depuis le 2026-10-24) : « Ajouter un Bibax » accepte un @nom (champ « Rechercher un Bibax ou un @nom »), et la recherche de l'accueil, pour une saisie qui commence par « @ », retrouve un compte, un lieu, une marque ou un producteur ; la casse est ignorée, il n'y a pas de recherche partielle et pas de nouveau réglage de confidentialité (mêmes informations visibles et mêmes blocages que pour le code ; un compte désactivé est introuvable). **Liens partageables `bibamus.app/@nom`** (depuis le 2026-10-24, dans l'app seulement) : « Compte → Nom d'utilisateur » montre « Ton lien » (à copier ou à partager) ; les fiches lieu, marque et producteur ont un bouton « Partager » qui partage ce lien (le lien général `bibamus.app` si la fiche n'a pas encore de @nom) ; les boissons n'ont pas de @nom et gardent le lien général ; le profil d'un autre Bibax n'a pas de bouton de partage. Ouvert par une personne connectée, le lien ouvre directement le compte (aperçu du profil), le lieu, la marque ou le producteur ; sans compte connecté, il est gardé sur l'appareil (24 h au plus, un seul à la fois) et ouvert juste après la connexion ou l'inscription. Un lien qui ne mène à rien (nom inconnu, compte bloqué ou désactivé, fiche non publiée) affiche toujours le même message neutre. **Fiches fusionnées — décision et mise en ligne du 2026-10-25** : quand une fiche est absorbée par une autre (statut « doublon »), son ancien lien continue de marcher et ouvre la fiche conservée — dans l'app, dans la recherche par @nom et pour les visiteurs sans compte (carte publique et aperçus de partage, avec le @nom de la fiche conservée) ; la redirection suit la chaîne si la fiche conservée est elle-même absorbée plus tard. L'ancien @nom est **libéré** (choix de Mehdi) : une autre fiche ou un compte peut le reprendre, et son nouveau porteur l'emporte alors toujours sur la redirection, même si sa page n'est pas visible (un compte, un brouillon, un compte qui a bloqué la personne). Pas de redirection non plus quand deux fiches absorbées ont porté le même nom (on ne devine pas) ni quand la fiche conservée n'est pas visible : le message neutre s'affiche. Rien à changer dans l'app pour cela (voir `DATABASE.md`). **Pages publiques — décisions du 2026-10-24** : une personne sans compte qui ouvre le lien d'un lieu, d'une marque ou d'un producteur verra une **carte résumé** (nom, photo, type, ville, pays, et un bouton « Ouvrir dans Bibamus » ; ni adresse, ni horaires, ni contact, ni produits) ; **seules les fiches « complet »** ont une carte ; cette carte est **indexable par Google** (pas de plan de site pour l'instant) ; **un compte n'a jamais de page publique** : le lien d'un compte et un nom inconnu donnent exactement la même réponse (écran de connexion, aperçu générique non indexé). **Livré** : la fonction de base `get_public_card` (en production depuis le 2026-10-24, voir `DATABASE.md`) ; les **aperçus de partage** (titre, description et image du lien dans WhatsApp, Messenger, Google, Telegram..., en production et constatés le 2026-10-25), produits par une fonction Vercel `api/at.js` que `vercel.json` réserve aux robots — une personne qui ouvre le lien reçoit l'app comme avant ; un compte, un nom inconnu ou une fiche pas encore « complet » donnent un aperçu général, identique et non indexé ; et, avec cette mise à jour, **la carte publique dans l'app** : une personne sans compte qui ouvre le lien d'une fiche « complet » voit d'abord la carte (nom, photo de profil et de couverture, genre — Lieu, Marque ou Producteur —, jusqu'à trois types, ville et pays, et le bouton « Ouvrir dans Bibamus »), puis l'écran de connexion ou d'inscription ; le lien reste mémorisé (24 h au plus) et ouvre la fiche complète juste après la connexion. Un compte, un nom inconnu, une fiche pas encore « complet » ou une base qui ne répond pas (délai de 6 secondes) mènent directement à l'écran de connexion, sans carte ni message, et de la même façon. Une personne sans compte qui revient sur le site dans les 24 h après avoir ouvert un lien revoit cette carte. **Pas encore construit** : changement du @nom par les gérants (plateforme Business), plan de site pour Google.

Faite côté base : trois fonctions de la liste filtrées, plus une fonction de recherche séparée `search_drinks_no_generic` (`searchDrinksNoGeneric` côté app). La lecture d'étiquette par IA les exclut aussi (`search_drinks_by_label`) ; la **carte boissons d'un lieu** les garde et peut en proposer (un lieu met souvent « Café » sans la marque). Détails et relevé dans `docs/DATABASE.md`.
- **Produits de la fiche Producteur par leur clé** — décision du 2026-11-09 (« les Produits sont tous liés aux marques et Producteurs côté Gestion ») : la carte « Ses produits » d'un producteur cherche ses produits par `drinks_directory.producer_ids` (fonction `get_drinks_by_producer_id`, `loadDrinksByProducerId`), comme la fiche Marque le fait avec `brand_id`, et non plus par le nom : l'ancienne recherche ratait les 704 produits liés sans texte `brewery`. Détails et relevé dans `docs/DATABASE.md`. Suite du 2026-11-10 : les 50 produits dont le texte « brewery » ne correspondait à aucun producteur sont réglés — 2 liés à leur producteur dans la plateforme de gestion, 48 produits génériques « Produits standards » dont le texte « brewery » a été vidé (un produit sans producteur a `brewery` à `NULL`). **Marques de la fiche Producteur (2026-11-10)** : la carte « Ses marques » restait vide (« Aucune marque liée à ce producteur pour l'instant ») alors que les marques étaient bien liées dans la plateforme de gestion : `brands_directory.producer_ids` est une colonne jsonb et le filtre de l'app était envoyé au format tableau Postgres, refusé par le serveur ; corrigé côté app seulement (`loadBrandsByProducer`), sans SQL. Détail dans `docs/DATABASE.md`.
- **Réseaux sociaux de la fiche Marque** — décision du 2026-11-09 (« il faudrait rajouter les réseaux sociaux, etc. ; ils sont encodés côté Gestion ») : la carte « Infos » d'une Marque montre, sous l'origine et sous un trait fin, la rangée d'icônes alignée à droite déjà utilisée par le Producteur (composants `buildSocials` et `SocialIconsRow`) : site, Facebook, Instagram, TikTok, Snapchat et YouTube — ce sont les colonnes que la table des marques possède (relevé du 2026-11-09) ; pas de téléphone, courriel, Google, WhatsApp ni LinkedIn pour une marque. Une marque qui n'a aucun lien ne montre pas la rangée. L'app ne fait que lire ces colonnes (`rowToBrand`), jamais les écrire. Les autres colonnes de la table, non lues par l'app : `slogan`, `founded_year`, `gallery_photos`, `video_links`, `brand_owner`, `current_producer`. **Lien YouTube (2026-11-10)** : côté Gestion, le début pré-rempli du champ YouTube des fiches Marque et Producteur est `https://www.youtube.com/channel/` (décision : « le "@" n'a pas lieu d'être » ; avant : `https://www.youtube.com/@`) ; l'app affiche le lien tel qu'il est enregistré. Les 37 liens déjà enregistrés en « `…/@UC…` » (identifiant de chaîne, inutilisable avec « @ ») ont été corrigés en `…/channel/UC…` par script le 2026-11-10. Détail dans `docs/ADMIN-PLATFORM.md` et `docs/DATABASE.md`.
- **BibaPulse : refonte des cartes, une sorte de carte à la fois** — décision du 2026-11-10 (« type d'interaction par type d'interaction ») ; première sorte : le **DrinkCheck** (`drink_checked`) ; deuxième : le **PlaceCheck** (`venue_visit`, check d'un lieu sans produit), copié sur le DrinkCheck. Le « @ » n'est pas adéquat pour un produit (il reste pour les lieux) : sous le rond de profil et le nom, une ligne « DrinkCheck » (icône du check, « Check » en vert fluo) avec la **note de l'auteur à l'extrême droite**, puis la **fiche du produit** en petit (rond de photo sur les trois premières lignes : nom ; sous-catégorie · drapeau · degré d'alcool séparés par un petit point vert fluo ; producteur — puis, sous le rond, contre le bord gauche : styles en pastilles, note moyenne), puis, si l'auteur a ajouté une photo et/ou un commentaire, un sous-bloc juste sous la fiche du produit (la photo entière, en petit, à gauche ; le commentaire à sa droite), puis le lieu du check, précédé de la pastille de lieu en vert fluo à la place du « @ » (« Taverne de Rome », « Home », « Event »). La rangée de réactions d'un DrinkCheck commence par le bouton Cheers (puis Bix, puis commentaire). L'icône Signaler (ou la corbeille pour ses propres cartes) est désormais toujours dans le coin bas droit du bloc des réactions, sur toutes les cartes. La barre oblique de la note de l'auteur est en vert fluo. Le rond de profil, la fiche du produit et le lieu ouvrent leur fiche, et **dans tous les cas le retour ramène à la carte d'où l'on est parti** (le fil, ou l'onglet BibaPulse de la fiche d'où l'on est parti, se rouvre sur elle, pas tout en haut ; les retours s'enchaînent en pile). Sur l'onglet BibaPulse de la fiche du produit lui-même, la fiche du produit n'est pas répétée. **PlaceCheck (2026-11-10)** : même ligne-titre (« PlaceCheck », icône du check de lieu), puis la **fiche du lieu** en petit (rond de photo sur les trois premières lignes : nom ; sous-titre précédé du point vert fluo ; adresse — puis, sous le rond : types d'établissement en pastilles), le sous-bloc photo + commentaire, « avec … », puis Bix / J'arrive ! / commentaire (pas de Cheers) ; le bloc ouvre la fiche du lieu et le retour ramène à la carte ; sur l'onglet BibaPulse du lieu lui-même, la fiche du lieu n'est pas répétée. Les autres cartes (Découverte, Ajout, BibaClub, publication libre) gardent leur présentation en attendant leur tour. Détail dans `docs/BIBAPULSE.md`. **Découverte (2026-11-10)** : un premier check sur Bibamus n'est pas une vraie découverte ; au premier check d'un produit, le formulaire DrinkCheck de la fiche produit propose la case « Je goûte ce produit pour la première fois » (décochée par défaut) — la carte n'est une Découverte que si elle est cochée. Check d'un produit depuis une fiche Lieu : ancienne règle, à revoir avec les PlaceCheck.
- **Fiche Producteur sur le modèle de la fiche Marque** — décision du 2026-11-09 (`BreweryDetailScreen`, `BreweryBrandDetailScreens.jsx`) : « le modèle en tout point des fiches Marques ». Faite en plusieurs étapes. **Étape 1 (faite, sans base de données)** : barre d'onglets `PillTabs` « Infos » / « BibaPulse » (à la place des deux boutons maison) ; onglet Infos = carte « Infos » **copiée de celle de la fiche Lieu** (décision du 2026-11-09 : « le bloc d'info, tu peux copier celui des Lieux » — mêmes cadre et pastilles de type, types puis profils du producteur ; trait vert ; adresse avec pastille de lieu et drapeau, qui ouvre Google Maps ; sans adresse, le pays et son drapeau ; le « B- » devant le code postal seulement pour la Belgique ; téléphone et courriel à droite de l'adresse, puis une rangée d'icônes de réseaux à droite (site, Google, WhatsApp, Facebook, Instagram, TikTok, Snapchat, LinkedIn, YouTube), sans les équipements ni Tripadvisor / Restaurant Guru des lieux — décision du 2026-11-09 : « c'est justement bien pour les Producteurs, on peut souvent aller visiter les lieux de production comme les brasseries » ; chaque rangée vide n'apparaît pas ; le « Lieu lié », s'il y en a un, vient dessous, après un trait fin), puis cartes « Ses marques (n) » et « Ses produits (n) » (regroupés par sous-catégorie) ; le pays quitte l'en-tête. Les blocs partagés avec la fiche Marque sont les composants `CardTitle`, `RelatedDrinksCard` et la ligne de lien `InfosLinkRow` (la fiche Marque, refaite avec eux et avec `EntityInfosCard`, s'affiche à l'identique) ; la carte « Infos » du Producteur est `ProducerInfosCard`. **Étape 2 (faite, avec des scripts SQL lancés à la main, voir `DATABASE.md`)** : cloche « Suivre sur Pulse » et cœur « Favoris » dans l'en-tête (« Partager » | cloche | cœur, comme la Marque ; la cloche est seulement enregistrée, sans effet sur le fil Pulse pour l'instant ; le cœur fait arriver en tête du fil les cartes du producteur, comme celui d'une marque — décision du 2026-11-09, voir `BIBAPULSE.md`), note sur 5 étoiles (bouton étoile et bannière de la couverture, fenêtre « Note ce producteur », droit de noter = avoir checké un produit du producteur, par `drinks_directory.producer_ids`) et onglet Biba360 avec la carte « Notes » (You / Bibax / Bibamus). Cloche, cœur et notes sont gérés par le même code que ceux de la Marque (`useEntityEngagement`). La fiche Producteur cherche toujours ses produits par le nom (`get_drinks_by_brewery`), pas par la clé `producer_ids`.
- **Une fiche Produit ou Lieu n'est jamais modifiable par un utilisateur** — règle rappelée par Mehdi le 2026-11-09 : seuls les **Admin Bibamus** (et, à terme, les **gérants** via Business) la modifient, sinon ce serait l'anarchie. Un utilisateur peut seulement **suggérer une modification** (bouton « Signaler ou suggérer une modification » de la fiche) ou **créer un produit/lieu inexistant** sur BibAtlas : il est alors **immédiatement disponible** sur BibAtlas, puis **vérifié et amélioré par les Admin Bibamus**. Conséquence sur les textes de l'app : ne jamais inviter à « ajouter » ou « modifier » une fiche existante, mais à y **suggérer une modification** (c'est ce que disent les avertissements de doublon des assistants d'ajout).
- **Onglets harmonisés (fiches Produits/Lieux, BibaClub, BibaRoom)** — décision du 2026-10-30 : un seul aspect, celui des fiches Produits et Lieux (composant `PillTabs`) : pastilles rondes, onglet actif plein vert fluo, **sans icônes**, avec un filet de séparation au-dessus et en dessous de la rangée. Un **BibaClub** a désormais trois onglets « BibaPulse » (ancien « Fil »), « Biba360 » (ancien « Stats ») et « Bibax » (ancien « Membres », le « x » en vert fluo), dans cet ordre ; seuls les libellés et l'ordre changent. Un **BibaRoom** garde « BibaRoom », « BibaPulse » et « BibaPing » avec leurs pastilles rouges de non lus, mais perd ses icônes.
- **Rond de profil des salons @Home / @Event** — décision du 2026-10-30 : un salon @Home porte une maison et un salon @Event un feu d'artifice (vert fluo, 62 % du rond) à la place du monogramme Bibamus par défaut ; la photo ou l'emoji d'un lieu reste prioritaire (voir `SalonAvatar`, `BIBAROOM.md`).
