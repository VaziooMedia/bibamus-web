## Geoapify

- **Autocomplétion d'adresse** (`AddressAutocomplete`, bibliothèque `@geoapify/geocoder-autocomplete`) : deux champs — code postal et commune — filtrés sur le pays ISO. La clé est `VITE_GEOAPIFY_API_KEY`, lue **par le navigateur** ; sans elle, « Auto-complétion non configurée ». Langue fixée à `fr` (pas celle de l'utilisateur). Utilisée par les assistants d'ajout de lieu et de producteur. **Commune et village (2026-11-26)** : Geoapify met le village dans `city` et la commune dans `municipality` (code postal 4950 : `city` = Robertville, `municipality` = Waimes), et il ne renvoie **qu'un seul village par code postal** (4950 → Robertville ; 4960 → Bévercé). À la sélection d'une suggestion, « Commune » reçoit donc `municipality` (Waimes), ou `city` si Geoapify ne donne pas de commune ; le village n'est jamais pré-rempli (le seul proposé serait faux pour la plupart des lieux du code postal), il reste à saisir dans « Section / Village ». Même règle dans l'app (`AddressAutocomplete.jsx`) et dans Gestion (sa propre copie). Les lieux déjà enregistrés ne changent pas. **Champ « Code postal » après le choix (2026-11-26)** : il n'affiche plus que le code (« 4950 »), la bibliothèque y écrivait auparavant le texte complet de la suggestion (« 4950 Robertville, Belgique ») ; le texte tapé avant le choix n'est pas touché. **Liste déroulante du code postal (2026-11-26)** : chaque suggestion s'affiche « code postal + commune » (« 4950 Waimes », repli sur la ville, puis sur le texte de Geoapify si le code postal manque), au lieu de « 4950 Robertville » avec « Belgique » dessous ; elle passe par `setPostprocessHook` de la bibliothèque, qui sert aussi au texte écrit dans le champ, d'où le retour au seul code postal après le choix (voir ci-dessus). La liste déroulante du champ « Commune » n'est pas modifiée. Pas vérifié hors Belgique : le contenu de `municipality` dans les autres pays (repli sur `city` s'il est absent). Essayé en simulation avec la vraie réponse de Geoapify pour 4950.
- **Commune du profil** (`CityAutocomplete`) : **pas Geoapify** — une liste statique `CITIES_BY_COUNTRY` (une quarantaine de pays), 6 suggestions au plus, texte libre accepté. Cette liste contient les deux variantes `Waimes` et `Weismes`.
- **Géocodage serveur** : la fonction Edge `geoapify-geocode` reçoit une adresse complète (assistant d'ajout de lieu **et assistant d'ajout de shop**, 2026-11-23 : pour un shop la position est envoyée **avec la création** — un compte de l'app ne peut pas modifier une fiche de shop après coup — et elle est remise à zéro si l'adresse change ensuite) ou seulement ville + pays (profil) et renvoie `lat`, `lng`, `status`, `source`, `confidence`. Source : **(base)**.

## PostGIS — établissements

- Colonne `location geography(Point,4326)` sur `public_venues`, synchronisée depuis lat / lng par le déclencheur `trg_sync_venue_location` (`BEFORE INSERT OR UPDATE OF lat, lng`, qui appelle la fonction `sync_venue_location()` : la position est vide dès que `lat` ou `lng` est vide) ; **relevé dans la base le 2026-11-25** : PostGIS 3.3.7, colonne de type `geography(Point,4326)` ; l'app n'écrit ni ne lit que `lat` et `lng`.
- RPC `get_nearby_venues(p_lat, p_lng, p_radius_meters, p_limit)` → lignes `{ venue, distance_meters }` **(base, relevée le 2026-11-25)** : valeurs par défaut 2 000 m et 10 lieux ; ne rend que les lieux aux statuts visibles (`to_process`, `to_fix`, `complete`) qui ont une position, du plus proche au plus loin ; fonction `STABLE` sans `SECURITY DEFINER` (les règles d'accès de la table s'appliquent à l'appelant) ; exécutable par `anon` et `authenticated`. Rayons réellement utilisés :

| Où | Rayon | Résultats |
|---|---|---|
| Suggestions à la création d'un salon | progressif 300 m → 1 km → 3 km → 10 km, jusqu'à 3 résultats | 8 au plus |
| Annuaire des lieux, « Lieux proches de moi » | 3 km | 8 |
| BibaSolo | 500 m | 2 (après @Home et @Event) |
| Fenêtre de check d'un produit | 5 km | 8 |
| Valeur par défaut | 2 km | 10 |

- `get_nearest_venues_serving_drink(p_drink_id, p_lat, p_lng, p_limit)` : les 5 lieux les plus proches (valeur par défaut de `p_limit`) qui proposent un produit (fiche produit) : un lieu « propose » le produit si un élément de son menu (colonne `menu`, jsonb) a `sourceDrinkId` égal à `p_drink_id` ; mêmes statuts visibles, même condition de position et mêmes droits que `get_nearby_venues` **(base, relevée le 2026-11-25)**.
- `get_venues_map_pins()` : pastilles de la carte, sans argument : rend `id`, `name`, `lat` et `lng` des lieux aux statuts visibles qui ont une latitude et une longitude ; `SECURITY DEFINER` (elle lit la table pour tout le monde, mais ne rend que ces quatre colonnes) ; exécutable par `anon` et `authenticated` **(base, relevée le 2026-11-25)**.
- **Traçabilité du géocodage** : `saveGeocodeResult` écrit `geocode_source`, `geocode_confidence`, `geocode_status`, `geocoded_at` (date du navigateur) sur `public_venues` **uniquement**, à la validation de l'assistant d'ajout de lieu et seulement si lat et lng sont renseignées. Valeurs de statut vues dans l'interface : `verified`, `exact`, `manual` ; le défaut `pending` est **(base)**. **Les producteurs ont aussi ces colonnes** (`geocode_source`, `geocode_confidence`, `geocode_status`, `geocoded_at` sur `breweries_directory` ; **vérifié sur la vraie base le 2026-11-25**, la doc disait le contraire) : le panneau Producteur de la plateforme de gestion les écrit par `saveBreweryGeocodeResult` dès que « Géocoder automatiquement » trouve une position, sur une fiche déjà enregistrée. Exemple lu dans la base : Brasserie des Fagnes → `geoapify`, confiance `0.75`, statut **`building`** (affiché « Précision : bâtiment » dans Gestion). Le géocodage lit rue, numéro, code postal, commune et pays (pas la section / village).
- PostGIS est installé dans le schéma `public` (voir `SECURITY.md`) **(base)**.

## PostGIS — proximité Bibax

- `get_bibax_suggestions(p_limit)` retient un candidat avec au moins un Bibax en commun (sans limite de distance), **ou** à 30 km ou moins (distance arrondie à l'entier), **ou** sans distance connue mais dans le même pays. Affichage « à X km » quand il n'y a pas de Bibax en commun (unité fixe en km). La proximité ne joue que pour les personnes qui partagent leur ville (`share_city`), et le repli par pays que pour celles qui partagent leur pays (`share_country`) ; les bloqués sont exclus. Détails : `BIBAX.md`.
- **Alimentation des coordonnées du profil** : `geocodeCityForProfile` est appelée quand la ville ou le pays changent, mais le résultat reste dans l'état de l'app — **le client ne l'envoie jamais à la base**. Si `profiles.latitude` / `longitude` sont renseignées, c'est par un autre mécanisme **(base)**.
- **Risque de non-déclenchement** : le géocodage cherche le code ISO avec `COUNTRY_ISO_CODES` indexé par code interne (`belgique`), alors que les écrans de profil enregistrent un libellé (`Belgique`). Dans ce cas la recherche ne trouve rien et le géocodage ne part pas. Deux tables `COUNTRY_ISO_CODES` coexistent (`constants.js`, par code interne ; `icons.jsx`, par libellé). La valeur réellement stockée dans `profiles.country` : **(base)**.

## Pays courant et âge légal en voyage

`TravelAgeWarning` (accueil) détecte le pays courant : la position GPS précise est envoyée à **`api.bigdatacloud.net`** (géocodage inverse côté navigateur, langue `fr`) qui renvoie un code ISO en minuscules. `getMinimumAge` interroge ensuite `market_config` avec ce code (valeur de repli : 18). Or les lignes de `market_config` sont indexées par **code interne** (`belgique`) : les scripts `bibamus-sql-1-verifier-doublon-belgique.sql` et `-2-supprimer-doublon-be.sql` ont supprimé la ligne `be` (valeur 16) et gardé `belgique`. Pour un code ISO, la recherche retombe donc sur 18 — l'avertissement pourrait s'afficher à tort pour un Belge de 16-17 ans en Belgique. **À vérifier** avec le contenu réel de `market_config`.

## Google Places — horaires d'établissements

Google est la **seule** source des horaires, jamais d'encodage manuel dans l'app (`OpeningHoursDisplay` : « Aucun formulaire »). La fonction Edge `google-place-hours` est appelée côté serveur pour ne jamais exposer la clé au navigateur (aucune clé Google dans l'app). Cache des horaires : 6 heures (`google_hours_cache`, `google_hours_last_fetch_at`). Statuts gérés : `OK`, `ERROR`, `LINK_REQUIRED`, `LINK_INVALID`, ouvert définitivement / temporairement fermé. **« Ouvert » / « Fermé » (corrigé le 2026-11-25)** : l'app **ne lit plus** `isOpenNow` du cache pour l'afficher (cette valeur est celle de l'instant de la lecture Google : un lieu lu à 08h43, fermé, restait « Fermé » après son ouverture de 09h00, constaté sur Taverne de Rome, horaires 09:00 - 01:00, cache lu à 08h43). Elle le calcule à chaque affichage d'après `google_hours_cache.days` et **l'heure de l'appareil** (`resolveOpenNow`, `isOpenNowFromDays` dans `src/openingHoursNow.js`), pour la fiche du lieu (`OpeningHoursDisplay`) et la pastille du cadre de la carte (`openStatusOf`, `venueMapCard.js`). Règles : une période dont la fermeture est avant ou égale à l'ouverture passe minuit (09:00–01:00 = jusqu'à 01h00 du lendemain, la fin de nuit d'hier compte pour aujourd'hui) ; « 23:59 » vaut minuit (Google coupe les journées à minuit) ; un jour absent ou « fermé » n'a aucune période. Sans horaires lisibles (`days` vide, jour ou heure illisible), l'app garde la valeur `isOpenNow` de Google, sinon rien n'est affiché. **Fuseau du lieu (code du 2026-11-25)** : les horaires sont ceux du lieu ; `resolveOpenNow` lit l'heure **du lieu** dans le champ `timeZone` du cache (nom IANA, ex. `Europe/Brussels`, calculé avec `Intl.DateTimeFormat`, heure d'été comprise), à défaut dans `utcOffsetMinutes`, et à défaut dans l'heure de l'appareil (`placeClock`). Un nom de fuseau inconnu passe au décalage, puis à l'appareil. **Côté fonction** : `google-place-hours` (nouvelle version de 150 lignes, **déployée par Mehdi le 2026-11-25 et vérifiée en conditions réelles**) demande à Google les champs `timeZone` et `utcOffsetMinutes` (Places API New : masque de champs `id,currentOpeningHours,regularOpeningHours,businessStatus,timeZone,utcOffsetMinutes`) et les écrit dans `google_hours_cache` avec le reste, dans les quatre réponses possibles (normale, fermé définitivement, fermé temporairement, sans horaires) ; `null` si Google ne les donne pas. Vérification : après avoir vidé la date de lecture de Taverne de Rome et rouvert sa fiche, le cache contient `timeZone` = `Europe/Brussels` et `utcOffsetMinutes` = 60, statut `OK`. Un cache plus ancien (6 h au plus, jusqu'à sa relecture) n'a pas encore ces champs : l'app garde alors l'heure de l'appareil, exacte pour les lieux du même fuseau que l'utilisateur. Simulé : même lieu, mercredi 09h38 à Bruxelles : « Ouvert » avec `Europe/Brussels`, « Fermé » avec `America/New_York` (03h38 là-bas). Le cache de 6 h reste utilisé pour ne pas appeler Google à chaque affichage. Simulé (Supabase simulé, fuseau Bruxelles) : 09h38 « Ouvert » (le cache disait « fermé »), 08h43 « Fermé » ; 30 cas testés (passage de minuit, mardi 09:00-23:59 + mercredi 00:00-01:00, vendredi et samedi jusqu'à 03h00, jour fermé, lieu sans horaires).

Les horaires servent à trois endroits : la fiche d'un lieu et la fiche d'un shop avec Magasin (`OpeningHoursDisplay`, bloc sous la carte « Infos » pour un shop ; absent d'un shop uniquement en ligne) et le cadre de la carte BibaMap (pastille ouvert / fermé).

**Shops (depuis le 2026-11-23)** : `shops_directory` a les mêmes colonnes Google qu'un lieu (`google_place_id`, `google_place_id_checked_at`, `google_hours_*`, `google_hours_cache`, `no_google_presence`, `no_fixed_hours`). Le lien se fait dans la plateforme de gestion, section « Horaires d'ouverture » de la fiche d'un shop (seulement s'il a un magasin ; un shop passé « En ligne » seul perd son lien à l'enregistrement). L'app lit `google_place_id`, `no_google_presence` et `no_fixed_hours` d'un shop (`rowToShop`) et ne les écrit jamais. `loadEstablishmentOpeningHours(googlePlaceId, table)` lit le cache de 6 heures dans `public_venues` (par défaut) ou dans `shops_directory` (shops : fiche et carte), puis appelle `google-place-hours` si le cache manque ou est périmé. **La fonction `google-place-hours` écrit le cache sur les deux tables** (`public_venues` et `shops_directory`, chacune sur les fiches liées à ce `placeId`) : nouvelle version (140 lignes) **déployée par Mehdi le 2026-11-23 et vérifiée en conditions réelles** : après avoir lié le shop « RJ Drink » à Google et ouvert sa fiche dans l'app, `shops_directory` contient `google_hours_cache` rempli, `google_hours_last_status = 'OK'` et une date de lecture récente.

`google-place-search` n'est appelée nulle part dans l'app : le rattachement d'un lieu à Google se fait dans la plateforme de gestion. Les messages « Pas d'horaire fixe » et « pas de présence Google » ne peuvent pas s'afficher aujourd'hui : les champs correspondants ne sont jamais chargés dans la fiche d'un lieu.

## Connu comme incomplet / non construit

- Proximité Bibax ↔ Bibax par position en direct : non construite (seule la ville déclarée compte). La position ponctuelle du navigateur est utilisée **pour les lieux**, pas pour les personnes.
- Coordonnées du profil jamais envoyées par le client ; correspondance ISO / libellé de pays à régler (voir plus haut). Idem pour `getMinimumAge`.
- Appels automatiques de position à aligner sur la règle écrite dans `useGeolocation` ; la position part à un tiers (BigDataCloud) à l'inscription et à l'accueil.
- Langue de l'autocomplétion fixée à `fr` ; préférence d'unité de distance non appliquée.
- Non vérifiable faute de scripts **(base)** : sources de `geoapify-geocode` et de `google-place-search` (PostGIS 3.3.7, la colonne `location`, le déclencheur `trg_sync_venue_location` et les fonctions `sync_venue_location`, `get_nearby_venues`, `get_nearest_venues_serving_drink` et `get_venues_map_pins` ont été **relevés dans la base le 2026-11-25** par une requête en lecture seule ; la source de `google-place-hours` a été livrée par Mehdi le 2026-11-25 : son comportement est décrit plus haut).
